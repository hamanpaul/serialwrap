- Rust 一般 agent line／background 命令只接受清理後行尾錨定的完整 echo；折行最多接受一個帶局部原始串流證據的 BusyBox／readline 插入點，其餘形態按無 echo 處理。完成與 stdout 使用同一 RX snapshot；stdout 從已確認的 echo 結尾擷取，不因輸出行尾等於命令而剝除。echo 後第一行恰好等於命令且後續還有輸出時，仍依狹義相容規則視為重複 echo；`completion_regex`／marker producer 維持既有結果。
- 無 echo 僅在命令起點沒有未結案 `pending_human`、窗口內沒有可信 human 訊號，且 snapshot 尾端最後一行通過完整 prompt 結案規則時相容完成。human 訊號包括起點 pending、窗口內 human submit 開始、human TX generation 變動及在途 submit（`human_in_flight`／`tx_submit_pending`）。任一訊號成立時不採相容完成，依既定等待上限回 `PROMPT_TIMEOUT`、`partial=true`、`recovery_action=NONE`，保留可用輸出、不送救援鍵。
- 所有 timeout 入口（靜默 chunk 與絕對 deadline）共用同一結算矩陣；有無 echo 不會讓 timeout 忽略 human 訊號。有訊號時回 `PROMPT_TIMEOUT`／partial／`NONE` 並抑制救援 TX；完全沒有 human TX／訊號時，`recover_after_failure` 的結果與 9af187ca 基線逐位元組相同，包括 status、錯誤碼、partial、recovery_action、輸出與救援鍵序列。operation deadline 到時若尚未線性化判定完成，不以 deadline snapshot 事後改判正常完成。
- 同一 session 的 bridge epochs 共用 human gate／計數域。僅在 OS write 成功返回後，才以 writer permit epoch 和 active RX watermark 登錄 human 邊界；只對 Accepted／Pending 建界，WouldBlock、NotSubmitted、拒絕不建界，且不跨 write 持有會阻塞 reader 的鎖。pending `(epoch, offset)` tuple 單調遞增；舊 epoch 晚登錄映射至 `(active_epoch, 0)`，接管把 pending 推至 `(new_epoch, 0)`。close fence 須待 writer／reader join、舊 handle close 及 WorkerStopped 回報後才開新 handle。
- prompt 結案只採完整清理視窗的真正最後一行：從可證明行首開始、完整符合目前 profile regex、終止於 snapshot 尾端，且整行原始來源位元組都在最新 TX 邊界後。`trimmed > 0` 且最後一行從保留窗口開頭起算時，行首無法證明；只有 `trimmed == 0` 且窗口起點是 epoch 串流起點才視為行首。分包未完整不結案，CR／重繪依 `clean_text` 語意處理。SetProfile／rematerialize 更新 gate regex 並保留 pending；確認 recover 後的 prompt 依同一尾端規則處理。
- timeout 發布 decision intent，並與 dispatch、human enqueue、pending 狀態變更在線性化臨界區仲裁，不依賴 mutex FIFO 公平性。human producer 只在 gate 內 `try_send`；queue 滿時釋放 gate 再等待容量。訊號讀取至多等待一個進行中的非阻塞 enqueue、一個 dispatch 及前一個 timeout 讀取區段，不等 writer 容量或 report。無 human 路徑保留 rescue reservation 至第一個救援鍵入列，新 human job 排在其後；deferred 按鍵只在實際產生 HumanTx effect 後計入在途，guard 隨 effect／pump／writer 傳遞並以 RAII 收斂。
- echo evaluator 命令起點已有 pending 且 timeout 選 human partial 時，只有在同一 decision reservation 中 submit 開始計數、human TX generation 與 pending tuple 都未變、`human_in_flight == 0` 且無 `tx_submit_pending` 時，才原子清除 pending 並記「timeout 消耗」；否則保留。此消耗不改本筆 partial、TX 或救援結果；決策前開始的 submit 保留 pending，決策後開始的 submit 建立新在途／pending。穩定 pending 在 human 無新動作時最多造成一筆 partial，之後回到基線；若消耗時 human 命令仍在裝置執行，後續也回到基線，因基線本無 human 保護而不會更差。舊 epoch pending 同樣適用。
- 四項保守代價各自最多造成一筆無 echo agent partial：prompt 在 write 返回前已完整抵達；Ctrl-L／方向鍵／Tab 等不送換行按鍵；無 echo 終端的無輸出 human 命令使 prompt 接在同一行；修剪後行首無法證明。有 echo 終端通常由 human 命令 echo 換行提供真實行首。
- issue 262 的 prompt 身分辨識與 issue 271 的同行 stdout 裁切仍由 i294-i2 處理；`completion_regex`、passthrough、Python 基線、錯誤碼集合與案例分母不變。
