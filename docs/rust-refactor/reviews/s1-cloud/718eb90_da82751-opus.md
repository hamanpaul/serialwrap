審查涵蓋 `upgrade_checks.py`、`run_upgrade_container.py`、`run-upgrade.sh`、`upgrade.Dockerfile`、`tests/test_docker_upgrade.py` 與 release 計畫。整體符合 OD-33 R2(b)：容器使用 `--network none`、不帶裝置、唯讀 mount；本機正式安裝不受影響；任一 FAIL 判 FAIL；缺項或 INSUFFICIENT 判 INSUFFICIENT；檢查 id 重複判 FAIL；docker 或 tag 缺少時以能力式 SKIP 標示證據不足，不判 PASS。已知升級問題照實列為 OBS 與兩個 PENDING-OD，沒有修改產品程式碼來掩蓋。以 v0.3.2 tag 的 `sw_core` 核對，`session.list` 的 session 帶有 `device_by_id`，alias 帶有 `session_id`／`device_by_id`／`profile`，`judge_state_compatible` 比對的欄位確實存在於基線輸出中。

1. [Low] `scripts/docker/run_upgrade_container.py:219-226`
   - 問題：`seed_user_data` 只檢查 `{"upgbench","pinned"}` 兩個 alias 存在，沒有檢查 `session bind` 確實生效。`judge_state_compatible` 的 binding 比對只會走訪基線中出現的 session。如果基線 `session list` 沒有列出 `shellboard:COM7`，或該 session 的 `device_by_id` 仍是 YAML 原值 `usb-UPGRADE_TEST…`，binding 相容檢查就形同沒做，但兩個 `state_compatible_*` 仍判 PASS。
   - 影響：changelog 與 addenda 宣稱的「alias／binding 遺失 → FAIL」在實跑中可能沒有被驗到。純函式測試 `test_alias_binding_lost_fails` 不受影響。
   - 修法：在 `ok` 條件加上 `any(s.get("session_id") == "shellboard:COM7" and s.get("device_by_id") == "/dev/serial/by-id/usb-UPGRADE_REBOUND-if00-port0" for s in self.baseline["sessions"])`，並把基線 sessions 寫入 detail。

2. [Low] `scripts/docker/run_upgrade_container.py:240-246`、`:334-341`

   - 影響：後續 `upgrade_after_stop` 會抓到損壞的 bundle，所以判 Low。但拒絕的語意本身沒有被 oracle 鎖住。
   - 修法：拒絕路徑另外要求 `body.get("error_code") == "METHOD_NOT_FOUND"`（rollback 則為 `INVALID_ARGS` 加上 `reason == "rollback_unavailable"`）。不符時判 FAIL，理由寫「拒絕原因與規格不符」。對應的純函式可抽出成 `judge_refusal(check_id, before, after, body, expected)`，並補一個「現場未改動但 error_code 不符 → FAIL」的測試案例。
