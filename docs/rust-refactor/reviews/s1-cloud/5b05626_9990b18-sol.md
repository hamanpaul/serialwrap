## B 新發現

**S1-9990b18-1 [Medium] `sw_core/session_manager.py:3682`（`bind_session` 無 bridge 分支，3713 spawn）— `session bind` 可繞過 OD-63，以佔位的 passthrough profile 真實 attach。**

問題：`43700f2` 把佔位實體化進 `_sessions` 後，`session bind` 不再回 `SESSION_NOT_FOUND`。它走既有的 RELEASED 解除路徑：

1. 丟棄 `_released_by_ids`。
2. 把 binding override 寫到佔位的 sid。
3. 呼叫 `_spawn_attach(device_by_id)`。

`_attach_by_id` 以 by_id 找到佔位。佔位的 `profile_source` 來自過期的 sticky 紀錄（`detected`），因此 `_reresolve_profile_on_reattach` 不重新偵測，直接以佔位 profile 開 bridge。這違反 DF-04 `approval_conditions`「佔位不可下命令、不以佔位 profile attach」，也違反 OD-63「交 template 偵測建立正式 session」。

重現（`_seed` 同 `tests/test_s1x_od63_released_placeholder.py`，`open_serial_port`→`FakePort`）：

- 輸入：`mgr.bind_session("COM3", "/dev/serial/by-id/usb-Z")`
- 預期：不得以佔位 attach，應交 template 偵測，或維持阻擋並指向 `device attach`。
- 實際：
  - `ok:true`，COM3 變成 `gone-template:COM3`、`ATTACHED`、`platform=passthrough`、`command_capable:false`，bridge 已開，`released_placeholder` 仍為 True。
  - state.json 的 released 清空，留下 `bindings{"gone-template:COM3": …}`。
  - COM3 在本次 daemon 存活期間無法下命令。

確切修法：

1. `bind_session` 的無 bridge 分支遇 `session.released_placeholder`，比照 `attach_session` 的 RELEASED 早退回 `{"ok":true,"released":true,"recommended_action":"device_attach","session":…}`。不解除阻擋、不寫 override、不 spawn；不新增 RPC／CLI 表面。
2. `_attach_by_id` 加防線：`released_placeholder` 的 session 一律不建 bridge。
3. 補回歸：佔位執行 `session bind` 後，COM3 仍為 RELEASED 佔位、零開埠；修正前會紅。

**S1-9990b18-2 [Medium] `sw_core/session_manager.py:3460`（`attach_device` 的 `except OSError` 分支）— 開埠遇一般 OSError 時佔位被移除，卻沒有交 template 偵測，裝置成為孤兒。**

問題：
- `DeviceHeldError`、`DeviceNotPresentError` 會保留佔位（有回歸）。
- 其他 OSError（如 dialout 權限不足的 `PermissionError`、`EIO`）會先 `_retire_released_placeholder_locked` 並解除阻擋，再回 `ok:true`＋DETACHED。但這條路不會 `_spawn_attach`，也不會留下任何 session。

一般 session 在同一路徑會保留 DETACHED 列，可以重試。現行 dynamic 開埠失敗也會由 `_record_dynamic_open_failure` 留下可診斷、可重試的 DETACHED session。佔位兩者皆無，與 OD-63「再交 template 偵測建立正式 session」不符。

重現：

- 輸入：佔位 COM3 在線、無 holder，`open()` 拋 `PermissionError(13)`，執行 `attach_device("COM3")`。
- 實際：
  - 回 `ok:true`，session 為 `DETACHED`，`last_error=ATTACH_FAILED:PermissionError`。
  - 之後 `_sessions` 為空、`_released_by_ids` 為空，沒有 attach 執行緒。
  - 修好權限後，`device attach COM3` 與 `session attach COM3` 都回 `SESSION_NOT_FOUND`。必須拔插或重啟 daemon 才能恢復。
- 預期：在原 COM 留下可再 attach 的列，或交 dynamic 偵測處理。

確切修法：

1. OSError 分支遇 `released_placeholder` 時，比照成功分支交接：retire 後設 `_pending_com[by_id] = 原 COM`。
2. 在 `_finish_attach_op` 與 `_save_state` 之後呼叫 `_spawn_attach(by_id, dynamic_only=True)`。dynamic 路徑會自行重開埠；仍失敗時由 `_record_dynamic_open_failure` 在原 COM 留下 DETACHED／`ATTACH_FAILED` 列。
3. 補回歸：`open()` 拋 `PermissionError` 後，COM3 必須仍可被 `device attach` 找到；修正前會紅。
