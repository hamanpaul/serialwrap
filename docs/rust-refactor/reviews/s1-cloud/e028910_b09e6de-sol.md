### `b09e6de`

- **判準正確。**`/proc/<pid>/exe` 取自 `task->mm->exe_file`，kernel 在 `begin_new_exec` 換 mm 之前就把 exe 設在新 mm 上，因此 exe 指向目標，就代表之後開啟的 environ 屬於新映像。
  - 新 mm 在 `create_elf_tables` 設定 `env_end` 之前，`environ_read` 依 `!mm->env_end` 回 0 byte；之後 `env_end` 一次設為最終值。所以「非空」即代表內容完整，不會讀到半截。
- **沒有放寬斷言。**`P4_DETACHED_ENV=supplied`、不含 `HOME=` 兩項斷言不變。3 秒期限到時是 panic，判 FAIL，不會轉成 SKIP。
- **其他面不受影響。**測試名稱不變（L1 鎖節點仍有效）；helper 以 `cfg(target_os = "linux")` 限定，與呼叫點的 cfg 一致；`rustfmt --check` 通過；正式 `spawn_daemon` 未改動。

### S1-b09e6de-1

[Low] [crates/sw-pal/tests/process_ctl.rs:58](crates/sw-pal/tests/process_ctl.rs:58) — 根因敘述不精確。

**問題：**helper 的註解、`b09e6de` 的 commit 訊息與 `changelog.d/s1x-b-r4-1-process-ctl-environ-exec-wait.md` 都把「讀到 exec 前（fork 自測試行程）的父環境」列為 spawn 回傳後可能發生的情形。但 POSIX `spawn_daemon` 走的是 std `Command::spawn`（`crates/sw-pal/src/process/posix.rs:99`），它以 CLOEXEC 錯誤管道等待：要等子行程已越過 exec 的不可回頭點（mm 已換、CLOEXEC fd 已關）才回傳。因此正式路徑實際可觸發的，只有「新映像的 env 區段尚未發布 → 0 byte」這一種窗口。

**實測**（暫時探針，放 scratchpad，未入 repo）：

- spawn 回傳當下讀 `/proc/<pid>/exe`，14,000 次都已指向 `/usr/bin/sleep`，0 次是父映像。
- 回傳後立即讀 environ：並行負載下 2,000 次中有 1 次讀到空內容。
- helper：7,000 次都讀到正確內容。

commit 所述「原讀法 30/30 紅（缺 P4_DETACHED_ENV、帶 HOME）」，是用一支未提交、在 exec 前就回傳的模擬工具測得的，不代表正式路徑。

**影響：**目前行為正確，exe 閘門是無害的防禦，沒有具體失敗情境。風險在後續維護者會依註解誤判根因。

**確切修法：**把註解與 changelog 改寫為「正式路徑（std `Command::spawn` 於 exec 後才回傳）可觸發的是 env 區段尚未發布時的空內容；exe 閘門用來防 spawn 實作改成 exec 前就回傳（例如 double-fork）時讀到父環境」。
