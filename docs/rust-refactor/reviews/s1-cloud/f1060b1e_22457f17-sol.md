## B 新發現

1. **[High] [crates/sw-cli/src/setup_cmd.rs:2014](file://crates/sw-cli/src/setup_cmd.rs#L2014) — setup 於 reconcile 前硬編碼 `restart_daemon: false`，stale daemon 從未被重啟、verify 介面未接通，且輸出偽 action 與遺漏 after/hint**
   - **問題：**
     Commit [`22457f17`](file://crates/sw-cli/src/setup_cmd.rs#L2069-L2097) 雖在 `run_setup` 加入了指紋讀取與評估，但將 [`install_layout::code_fingerprint`](file://crates/sw-cli/src/install_layout.rs#L1351)、[`daemon_code_assessment`](file://crates/sw-cli/src/setup_cmd.rs#L920) 與 [`select_daemon_restart_action`](file://crates/sw-cli/src/setup_cmd.rs#L991) 放在 [`reconcile`](file://crates/sw-cli/src/setup_cmd.rs#L2016) **之後**才計算，並在 [`ReconcileRequest`](file://crates/sw-cli/src/setup_cmd.rs#L2000-L2015) 硬編碼 `restart_daemon: false`。
     這導致：
     1. `reconcile` 永遠以 `restart_daemon = false` 運行。在已安裝並運行舊指紋 daemon 的 `systemd-user` 或 `systemd-system` 模式下，即便指紋過期（stale），`setup` **完全不會發送重啟命令**（`systemctl --user restart serialwrap` 或 `sudo systemctl restart serialwrap`），舊 daemon 繼續常駐跑舊碼，違背 #241 升級換新碼的核心目的；在 `systemd-system` 無 sudo 時，也不會將重啟加入 `pending_sudo`。
     2. [`verify_daemon_code_after_restart`](file://crates/sw-cli/src/setup_cmd.rs#L1667) 在產品程式碼路徑中從未被呼叫（新增介面未接上正式呼叫路徑）。
     3. [`daemon_code_value`](file://crates/sw-cli/src/setup_cmd.rs#L1633) 直接輸出 `restart_action.as_str()`，對外輸出 `"action": "restart"`。這不是 Python 基線的合法終態（Python 基線在完成重啟與驗證後輸出 `"restarted"`，在需 sudo 時輸出 `"pending_sudo"`，在失敗時輸出 `"restart_failed"`，從不輸出 `"restart"`，見 [`sw_core/cli.py:2008-2023`](file://sw_core/cli.py#L2008-L2023) 與 [`contracts/cli_schema.json:3222-3233`](file://contracts/cli_schema.json#L3222-L3233)）。
     4. 對外 JSON 輸出完全遺漏 `"after"` 欄位與 `hint`（Python 與 schema 明確要求重啟後填寫 `after`，並依 action 輸出中文提示 `hint`）。
   - **具體失敗情境：**
     在 `systemd-user` 監管模式下，本機原有舊版 daemon 執行中（回報舊程式碼指紋 `old_fp`），以新版 bundle 執行 `serialwrap setup`（或 `serialwrap setup --systemd-user`）：
     - **預期輸出／行為（Python 1:1，見 [sw_core/cli.py:1922-2029](file://sw_core/cli.py#L1922-L2029)、[tests/test_build_fingerprint.py:355-380](file://tests/test_build_fingerprint.py#L355-L380) 與 [contracts/cli_schema.json:3208-3253](file://contracts/cli_schema.json#L3208-L3253)）：**
       1. 呼叫 `systemctl --user restart serialwrap` 重啟 daemon，`setup` 回應含 `daemon_restart: "ran"`；
       2. 以 `health.ping` 輪詢驗證新 daemon 就緒且回報新指紋 `new_fp`；
       3. `daemon_code` 輸出：`{"stale": true, "reason": "fingerprint_mismatch", "daemon": "old_fp", "installed": "new_fp", "action": "restarted", "after": "match"}`。
       （若在 `systemd-system` 無 sudo 時，將 `sudo systemctl restart serialwrap` 加入 `pending_sudo`，`daemon_code.action` 為 `"pending_sudo"` 並附 `hint`；非重啟分支如 `manual_restart` 亦附提示字串）。
     - **實際輸出／行為（commit [`22457f17`](file://crates/sw-cli/src/setup_cmd.rs#L2014)）：**
       1. 未呼叫任何 systemctl restart，舊 daemon 未重啟且繼續常駐；
       2. `setup` 中 `daemon_restart` 為 null 或未設定；
       3. `daemon_code` 輸出：`{"stale": true, "reason": "fingerprint_mismatch", "daemon": "old_fp", "installed": "new_fp", "action": "restart"}`；
       4. 缺失 `"after"` 欄位；
       5. 缺失 `"hint"` 欄位；
       6. [`verify_daemon_code_after_restart`](file://crates/sw-cli/src/setup_cmd.rs#L1667) 未被執行。
   - **確切修法：**
     在 [`crates/sw-cli/src/setup_cmd.rs:run_setup`](file://crates/sw-cli/src/setup_cmd.rs#L1887) 中：
     1. 將 `installed_fingerprint`、[`daemon_code_assessment`](file://crates/sw-cli/src/setup_cmd.rs#L920) 與 [`select_daemon_restart_action`](file://crates/sw-cli/src/setup_cmd.rs#L991) 移至呼叫 `reconcile` 之前；
     2. 當 `restart_action == DaemonRestartAction::Restart` 時將 `req.restart_daemon` 設為 `true`；
     3. `reconcile` 回傳後檢查 `setup.get("daemon_restart")`：
        - 為 `"ran"`：`action` 轉為 `"restarted"`，呼叫 [`verify_daemon_code_after_restart`](file://crates/sw-cli/src/setup_cmd.rs#L1667) 填入 `"after"`（`match`／`mismatch`／`unreachable`）；若非 `match` 則輸出 stderr 警告並設定 `hint`；
        - 為 `"pending_sudo"`：`action` 轉為 `"pending_sudo"` 並設定對應 `hint`；
        - 為 `"failed"`：`action` 轉為 `"restart_failed"` 並設定對應 `hint`；
     4. 若為跳過重啟分支（如 `skipped_no_restart_flag`、`manual_restart`、`skipped_flashing`、`service_inactive`），補入與 Python `_DAEMON_CODE_HINTS` 一致的中文 `hint`。

2. **[Medium] [tests/test_s1m241_cli_fingerprint_parity.py:177](file://tests/test_s1m241_cli_fingerprint_parity.py#L177) — 回歸測試在未修復重啟缺陷時不會紅燈**
   - **問題：**
     [`tests/test_s1m241_cli_fingerprint_parity.py`](file://tests/test_s1m241_cli_fingerprint_parity.py#L177) 新增的唯一測試 [`test_s1m241_setup_current_manifest_is_reported`](file://tests/test_s1m241_cli_fingerprint_parity.py#L177) 僅覆蓋了 `--on-demand` 且指紋吻合（`action == "none"`）的單一案例。對於 stale daemon（不同指紋或缺指紋）在 systemd 模式下應觸發重啟、驗證 after 與轉換 action 的正式行為，該檔完全沒有任何回歸測試，致使 S1-22457f1-1 的重大行為缺失完全未被黑箱回歸網攔截，測試依然全綠通過。
   - **具體失敗情境：**
     在目前 `crates/sw-cli` 存在 S1-22457f1-1 缺陷的狀態下執行 `python3 -m pytest -q tests/test_s1m241_cli_fingerprint_parity.py`：
     - **預期：** 測試套件應含有比對 stale daemon 重啟與指紋驗證的黑箱測試，並在目前未重啟、action 不對齊的情況下亮紅燈 **FAIL**。
     - **實際：** 測試套件只有 matching on-demand 單一案例，執行結果為 `1 passed in 4.98s`，失去保護作用。
   - **確切修法：**
     在 [`tests/test_s1m241_cli_fingerprint_parity.py`](file://tests/test_s1m241_cli_fingerprint_parity.py) 增加 stale daemon（例如舊 daemon 指紋不符）的測試案例，斷言 CLI 在相應情境下的外部輸出（包括重啟後的 `action: "restarted"`、`after: "match"` 等），要求在缺陷存在時必然紅燈。
