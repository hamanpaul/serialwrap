## B 新發現

**S1-109f659-1 [Medium] `contracts/rpc_schema.json:4304`（`session.bind`；x-order 在 `:4337`，side_effects 在 `:4376`）／`sw_core/session_manager.py:3586` — `5e7c970` 讓 `session.bind` 多了一個成功回應分支，卻沒登記到 RPC 契約目錄。**

問題：

- 輸入：OD-63 佔位 COM3 執行 `session.bind {"selector":"COM3","device_by_id":"/dev/serial/by-id/usb-Z"}`。
- 實際：
  - 回應鍵為 `["ok","released","recommended_action","session"]`。
  - 不 detach、不離開 RELEASED、不寫 `_binding_overrides`、不 spawn。
- 契約預期：
  - `x-methods.session.bind.result` 只宣告 `ok`／`already_bound`／`session`，`x-order` 為 `["ok","already_bound","session"]`，沒有 oneOf 分支。
  - `side_effects` 的 on_success 寫的是「detach（REBOUND）、離開 RELEASED、`_binding_overrides[sid]=by_id`、`_save_state()`、spawn attach」。
- 以契約測試 `test_self_test_recover_branch_orders_match_source_literals` 所用的 `_admits()` 判準實測，結果為 `False`（`undeclared=['recommended_action','released']`）。
- 以 AST 掃 `session.bind`、`session.clear`、`device.attach`、`session.attach` 全部 `ok:true` 字面回應，只有這一處不被 schema 接受。同形狀的 `session.attach` RELEASED 分支、`session.recover` RELEASED 分支、`session.clear` 的 `released` 都已登記。
- 影響：P5～P8 依契約目錄實作 Rust `session.bind` 時，不會產生這個分支，也會把佔位 bind 當成「離開 RELEASED」，與 Python 基線分歧。現有測試全綠，攔不到。
- 先例：本分支 `5b05626`（OD-62）改 RPC 回應時同步改了 `rpc_schema.json`，CLAUDE.md 也要求「顯式同步多個表面」。

確切修法：

1. 在 `contracts/rpc_schema.json` 的 `session.bind.result` 做 add-only 修改：
   - properties 加 `released`（`boolean`、`const: true`）與 `recommended_action`（`string`）。
   - `x-order` 改為 `["ok","already_bound","released","recommended_action","session"]`。
   - 或者比照 `session.recover` 改為 oneOf，另立 `x-branch: "RELEASED"` 分支。
2. `side_effects` 補一筆，帶 `x-condition`：「OD-63 佔位：早退，無副作用」。
3. 依檔內慣例處理 `x-catalog-revision`。
4. DF-04 的 `compatibility_impact` 補上 bind 對佔位的早退行為。
5. 補契約回歸：以 `_source_literal_orders("sw_core/session_manager.py", {"bind_session"})` 搭配 `_admits()`，驗每個字面回應都被 `session.bind` 的 schema 接受。這個回歸在修改 schema 前會紅。

**S1-109f659-2 [Low] `sw_core/session_manager.py:3583` — 佔位的舊裝置永久不回來時，沒有任何 RPC／CLI 出口可移除佔位。**

問題：佔位 COM3（by_id Z）的舊板 Z 已退役，只有新板 usb-NEW 在線。實測各操作結果：

| 操作 | 結果 |
|---|---|
| `session bind COM3 usb-NEW` | `ok:true`、`released:true`、`recommended_action:"device_attach"` |
| `device attach COM3` | `DEVICE_NOT_PRESENT` |
| `session clear COM3` | `ok:true`、`released:true` |
| `session attach COM3` | `released:true` |
| 重啟後 | 仍為 RELEASED 佔位 |

- COM3 與一個 `max_sessions` 名額永久被占用，`recommended_action` 指向的動作也做不到。
- 只能把舊 template 名稱加回 profiles，或手改 state.json。
- 在 `9990b18`，bind 會解除佔位，雖然那正是 S1-9990b18-1 的缺陷路徑。
- OD-63 與 DF-04 沒有定義這個情境，觸發需同時滿足三個條件（已 release、template 已刪、舊板永久離線）。因此列 Low，不擋放行。

建議（需擁有者或編排者擇一）：

- (a) bind 目標 by_id 在線時，佔位 retire 自身（比照一般 RELEASED bind 的「離開 RELEASED」）。再以 `_pending_com[target]=原 COM` 加 `_spawn_attach(target, dynamic_only=True)` 交 template 偵測，不以佔位 profile attach，也不新增 RPC／CLI 表面。
- (b) 追認為已知限制，在 README（中英）與 openspec 寫明處置方式。
