[Low] `docs/rust-refactor/owner-runbook-od29.md:46`（「不改為…的理由」那一句）— 文中說 Python 基線「無委派層，`python.exe` 對 Ctrl+Break 採預設處置直接結束」，因此忽略 Ctrl+Break 是「Python 基線沒有的新行為」。這個前提與 Python 基線的 Windows 發佈形態不符。Windows 版 `serialwrap.exe` 是 PyInstaller one-file：bootloader 父行程就是委派層，它對 Ctrl+C 與 Ctrl+Break **都**忽略，並原樣回傳子行程的結束碼（核對 #2）。目前功能面沒有可觀察的差異，因為 `sw_core` 沒有註冊 Ctrl+Break（SIGBREAK）的處理器，子行程同樣以 `0xC000013A` 結束。但如果子行程對 Ctrl+Break 做清理或以自訂碼結束，兩邊的結果會不同。舉例：子行程攔截 Ctrl+Break 後以 `exit 77` 結束。Python one-file 回傳 77；Rust 委派者本身先以 `0xC000013A` 結束，而在 `kill_on_close` 路徑上，關閉 job 會連帶殺掉還在清理中的孫行程。這段錯誤的理由已記成審查 ACCEPT 的依據，日後可能被引用來排除這項差異。 — 確切修法：改寫這一句。刪除「Python 基線無委派層」的敘述，改為：「Python 基線的 Windows release（PyInstaller one-file）的 bootloader 對 Ctrl+C／Ctrl+Break 都忽略，並照傳子行程結束碼；Rust 委派者只忽略 Ctrl+C。由於 `sw_core` 沒有 SIGBREAK 處理器，兩者對使用者可觀察的結束碼目前相同，所以本輪不改案例形狀。這項差異登記為已知差距，交擁有者裁定是否讓委派者一併忽略 Ctrl+Break（若裁定要改，就採用前輪 d0b8ad7#1 的特徵碼 77 案例）。」並在 addenda 新增一條對應的 CHG 條目，狀態寫「待擁有者裁定」。
