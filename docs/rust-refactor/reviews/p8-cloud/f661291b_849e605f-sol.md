## B 新發現

**P8-849e605-1 [High] — [session_manager.rs:1196](crates/sw-core/src/session_manager.rs:1196)：未接受的 handle 改為非同步關閉後，release 可在 UART 尚未關閉時回成功。**

具體失敗情境：

1. 佔位退休落盤失敗，留下 B3 的 parked handle；COM0 原裝置離線，進入 DETACHED。
2. `bootstrap_attach → rebind_detached` 將 COM0 改綁 B3，把 handle 存為 `Held{Worker}`；在 binding 落盤處暫停。
3. 經正式 `SessionManager::route` 提交 COM0 的 `Release`，確認進入 RECOVERING、等待 attach 作業。
4. 放行落盤。`BeginExternalAttach` 因 release 停止中而拒絕，進入 `close_unoffered_custody`；暫停實際 close。

**預期：** close 回條前不得成功；超過首次期限應回 `DRAIN_STALLED`。

**實際：** close 仍暫停、`is_open=true`、帳本仍為 `Closing{job:"unoffered"}`、原 token 沒有 terminal，release 已回：

```text
ok=true
session.state=RELEASED
session.drain_stalled=false
session.drain_timeout_epoch=null
```

根因：本輪改為啟動 closer 後立即返回，卻保留 `Worker` owner；新增的 [finish_worker_op 等待條件](crates/sw-core/src/session_manager.rs:2815)只等待 `Reaper` owner，於是跳過關閉等待，再於 [2925 行](crates/sw-core/src/session_manager.rs:2925)把 release watch 結算為成功。這違反規格 §5.2.4，以及 Python `release_device` 等待 attach 作業完成後才回成功的語意。

**確切修法：** 非同步交出 unoffered handle 時同步轉移關閉責任，保留 attach 作業與 release watch，直到同 token 的實際關閉終態到達；依該終態結算成功或失敗，不能因 worker 本體返回而填入成功。補上上述交錯，涵蓋 close 暫停、成功及失敗。
