**發現**

1. **[High] `crates/sw-core/src/session_core.rs:2119`（相關：`:2300` `apply_quiet_armed`）— attach 登入期間收到 boot banner，session 會永久卡在 ATTACHING。**
   - **原因**：`apply_quiet_armed` 會把 `fsm_gen` 加 1。attach 路徑的 `LoginFinished` 要求 `fsm_gen` 相等，於是登入 thread 回來的結果（TX 被 Quiet／FsmMismatch 拒絕後回 `NotReady("PROMPT_UNAVAILABLE")`）被直接丟棄。
   - **後果**：bridge 沒被採用，`login_run` 一直殘留，之後 `SessionAttach` 還回 `ok:true`。
   - **實證**：在 repo 外的副本用 CoreHarness 重現。依序 DeviceAttached → bridge_ok → rx 收到 U-Boot banner → 以舊 `fsm_gen` 送 `LoginFinished(NotReady)`，結果 state 停在 `Attaching`，SessionAttach 回 `ok=true`。
   - **Python 的行為**：arm 時 `login_gen+1`，之後的 TX 被 `quiet`／`stale_login_gen` 拒絕，走 `probe_refused` 分支，結果是 ATTACHED＋`PROMPT_UNAVAILABLE`。這正是 DUT 重開機時重新 attach 的 #130 常見情境。
   - **修法**：
     - `LoginRun` 記下自己的 `fsm_gen`；
     - attach run 改以 `run.epoch == epoch && run.kind == Attach && run.fsm_gen == fsm_gen` 比對，不比對 core 目前的 `fsm_gen`；
     - 結果照 Python 套用：NotReady→ATTACHED，Ready→READY＋`confirm_ready`，Failed→drain；
     - 補回歸測試 `banner_during_attach_login_settles_attached`，並 add-only 入鎖。

2. **[Medium] `session_core.rs:2326` `reboot_tx_settled`／`tx_writer.rs:572` — reboot 的 quiet 是非同步生效的，和 Python 的保證不同。**
   - Python `_handle_reboot_command` 在同一個 `_write_lock` 內 arm，保證下一個 UART writer 取得鎖之前 quiet 已生效。
   - Rust 的 TxWriter 送出 `UartTxCompleted` 後會立刻處理下一個 job，要等 actor 處理到這個事件才會設 fence 的 `quiet_active`。中間的窗口裡，受 quiet gate 管的 LoginProbe、ReadyReconfirm、SelfTestProbe、SystemRecoverKey 都可能被放行。
   - **修法**：
     - 在 `TxPermit` 加 `arms_quiet_on_submit`（前景 reboot 命令時為 true）；
     - TxWriter 在記錄結果的同一個 `Fence::with` 內，遇到 confirmed>0 或 Unknown 時同步設 `quiet_active=true`、`reconfirm_pending=true`；
     - actor 之後只負責同步 `QuietState`；
     - 補測試：reboot job 後面緊接一個 LoginProbe job，必須被 `FenceReject::Quiet` 拒絕。

3. **[Medium] `crates/sw-core/tests/login_quiet.rs:499–556` — reboot 測試從 ActorRig 端到端測試降成 sans-IO。**
   - `reboot_command_arms_quiet_at_dequeue` 原本經真 actor 與 TX 路徑；現在改用 CoreHarness 手動合成 `UartTxCompleted{op_id: grant.op_id}`。
   - 結果沒有任何測試證明真 OpRunner／TxWriter 的 TX `op_id` 等於 grant 的 `op_id`，而 `reboot_tx_settled` 正是靠這個等式判斷。
   - `reboot_not_submitted_does_not_arm_quiet` 也沒有照計畫用 `fence.freeze()` 或 StaleEpoch 實際拒絕 TX。
   - **修法**：保留現有 sans-IO 測試，另加 ActorRig 版（例如 `reboot_command_arms_quiet_after_tx_submitted_actor`、`reboot_frozen_fence_not_submitted_actor`）。T14 完成前允許紅燈，並 add-only 入鎖。

4. **[Medium] `crates/sw-core/src/login_fsm.rs:306–314` — 任何非 `Completed(n≥len)` 的 TX 結果都被當成 `PROMPT_UNAVAILABLE`。**
   - Python `_login_tx_refused` 只把 `quiet`／`stale_login_gen` 收斂成 `PROMPT_UNAVAILABLE`。其他情況都 re-raise，包括 Unknown（`TxUnknownError`）、`wal_unhealthy`（`WalUnavailableError`）、draining、cancelled、部分寫入。
   - re-raise 後，attach 路徑變成 DETACHED，`last_error` 為 `ATTACH_FAILED:<ExcType>`；既有 bridge 再探路徑則是例外直接穿出。
   - 例：login probe 的 TX 結果為 Unknown 時，Python 是 DETACHED＋`ATTACH_FAILED:TxUnknownError`，Rust 是 ATTACHED＋`PROMPT_UNAVAILABLE`。
   - 程式註解「Python TxIncompleteError → PROMPT_UNAVAILABLE」與 Python 不符。計畫裡 disk_full 案例期望 WalUnhealthy→`PROMPT_UNAVAILABLE`，這也和 Python 衝突。
   - **修法**：依 `TxReport.reject` 分流，Quiet／FsmMismatch→`PROMPT_UNAVAILABLE`，其餘照 Python 映射；或在 `contracts/behavior_changes.yaml` 登記 BC/SC，經 owner 核准，並修正註解。

5. **[Medium] `session_core.rs:2240`（經 `:2056` 的 `choose_plan`）— 再探把 `pending_auto_login` 算進 `require_login`。**
   - Python `_probe_existing_bridge` 只看 `login_regex` 與 `console_unlock_env`。
   - Python attach 失敗的分支不清 `pending_auto_login`，所以 session 在 ATTACHED 時這個旗標可能為真。
   - **實證**：profile 沒有 `login_regex`、宣告了 `user_env`／`pass_env` 但未解析、`pending_auto_login=true`，此時 Rust 再探回 `CREDENTIALS_UNRESOLVED`，Python 會走 `probe_ready`。若帳密已解析，Rust 走 EnsureReady，Python 仍走 probe。
   - **修法**：再探路徑以 `pending_auto_login=false` 呼叫 `choose_login_plan`，或另寫 reprobe 專用的計畫選擇，並補測試。

6. **[Low] `login_fsm.rs:117`、`session_core.rs:2003/2226` — quiet gate 沒有排除 `console_unlock_env`。**
   - Python `_boot_quiet_blocks_probe` 是 `boot_quiet_active() and not console_unlock_env`。
   - 宣告了 `console_unlock_env` 但未解析時，quiet 期間 Python 回 `CREDENTIALS_UNRESOLVED`，Rust 回 `PROMPT_UNAVAILABLE`。
   - **修法**：`quiet_blocks = quiet_active(now) && !declared(console_unlock_env)`。

7. **[Low] `session_core.rs:2116` — 再探的 `LoginFinished` 遇到 `state != Attached` 直接 return，沒有 `take` 掉 `login_run`，等待者永遠收不到回覆。**
   - 目前 2.1 只有 `begin_stop` 會讓 session 離開 ATTACHED，而它已經處理等待者，所以現在還沒發生，屬於潛在問題。
   - **修法**：take 掉 run，照 Python 回 `STATE_CHANGED`（FLASHING／RELEASED）或 `attach_state_result`。

8. **[Low] `session_core.rs` `reprobe_existing_bridge` — 並發的第二個 SessionAttach 會併入第一個 run，直接拿它的結果。**
   - Python 是用 `probe_lock` 排隊，輪到時再跑一次 probe（會多一次 TX）。
   - **修法**：照 Python 排隊再跑，或把這個差異登記為 SC。

9. **[Low] 證據追溯與命名（`login_quiet.rs:556`、計畫 Task 13 表）。**
   - `reboot_command_arms_quiet_at_dequeue` 為了 add-only 鎖保留舊名，但斷言語意已經相反。
   - 計畫列「username／user_env 皆無 → `LOGIN_USER_REQUIRED`」，這一列被改成無 pass_env→`SHELL_PROMPT_TIMEOUT`。改完後 `LOGIN_USER_REQUIRED` 只剩 X3 情境有覆蓋。
   - 文中提到的「Python 實測」（READY_PROMPT_TIMEOUT、X3、SHELL_PROMPT_TIMEOUT）沒有提交 Python 特性測試，只能靠 commit message 追溯。
   - 計畫寫的「#93 寫 WARNING」和「USER_ENV_MISSING 列」也沒有回寫到 parity-amendments。
   - **修法**：
     - 在 `tests/test_login_fsm.py` 補上述四個值的 Python 特性測試；
     - 補一列「無 username／user_env、宣告 pass_env → `LOGIN_USER_REQUIRED`」；
     - 在 `parity-amendments-2026-10-26.md` 登記這些與計畫的差異，並在測試 docstring 寫明舊名的語意已依 #55 改變。
