## B 新發現

- **P5-54dd588-1 [Medium]** `crates/sw-pal/tests/lock.rs:35`（`lock_conformance_suite_survives_concurrent_spawns`）；受害測試在 `:117`、`:215`／`:276`
  - 問題：新測試在 `lock` 測試執行檔內，以背景執行緒連續 spawn 子行程，同時跑 1000 輪 lock_suite（約 2 s）。libtest 預設平行執行，所以同檔其他測試在這段時間大量暴露在 F206 自己指出的 fork→exec 視窗裡：子行程在 exec 前持有父行程全部 fd 的複本。lock_suite 本身已改成只 bind 不 listen，但同檔另外兩支凍結必要測試仍會中：
    - `stale_socket_is_unlinked_then_acquired`（`:117`）：仍以 `UnixListener::bind`→drop 製造失效 socket，探測連到子行程手上的 listener 複本，得 `AlreadyRunning`（`:127` unwrap）。
    - `socket_probe_eacces_is_socket_unavailable`（`:215`）：第一次 acquire 失敗並關閉 lock fd，但子行程的 fd 複本仍持有 flock，第二次 acquire 得 AlreadyRunning 而非 SocketUnavailable，`:276 assert!(second)` 失敗。
    - 兩支都在 `s21_core.linux` 與 `s21_gate:linux_cap_posix_pty.linux`。gate 的 `linux_l1` 與 `linux_cap_posix_pty` 都以預設平行模式執行這個執行檔。
  - 失敗情境（實跑；uid 1000、4 核；54dd588 debug 建置的 `lock-f12e35e93d85819b`；整檔連跑 300 次）：

    | 條件 | 失敗次數／300 | 失敗內容 |
    |---|---:|---|
    | 預設（含新測試） | 4 | `stale_socket_is_unlinked_then_acquired` ×3（AlreadyRunning）；`socket_probe_eacces_is_socket_unavailable` ×1（`assertion failed: second`） |
    | `--skip lock_conformance_suite_survives_concurrent_spawns` | 0 | — |

    預期：修 flake 的 commit 不得引入新的間歇失敗（CLAUDE.md 測試政策）。實際：每次 gate 這兩個 section 各約 1.3% 機率紅燈。
  - 確切修法：
    - 把壓力測試移出共用行程。做法一：測試本體以 `current_exe()` 重入自身 `--exact lock_conformance_suite_survives_concurrent_spawns --test-threads=1`，以環境變數區分子行程（比照同檔 `socket_probe_eacces_is_socket_unavailable` 的作法），spawner 執行緒只存在於子行程。做法二：移到獨立的整合測試檔（如 `crates/sw-pal/tests/lock_spawn_stress.rs`），新 nodeid 依 add-only 登記。
    - `stale_socket_is_unlinked_then_acquired` 屬同一根因，改用與 lock_suite 相同的只 bind 不 listen 建立失效 socket（把 `bind_without_listen` 開放給測試使用）。
    - 驗證：同上 300 次整檔迴圈須 0 失敗。

## 既有碼待辦（不計入結論）

1. F206／F208 指出的根因同類問題（平行測試執行檔內 fork→exec 視窗的 fd 複本），在凍結必要集合中還有未修的實例：
   - `crates/sw-pal/tests/fs_lock.rs:34` `file_lock_nonblocking_contention_wouldblock`：本審 4 次 linux_cap_posix_pty 實跑中紅 1 次（`:50`「第一個 guard drop 後應可再次取得鎖」）。同檔 `file_lock_cross_process` 會 spawn 子行程，子行程的 fd 複本持有 flock。
   - `crates/sw-pal/tests/lock.rs:117` `stale_socket_is_unlinked_then_acquired`：仍用 bind→drop。不含新測試時雖為 0/300，但與 lock_suite 原本的問題相同。

   建議一併改為不依賴排程的固定前置，或把會 spawn 的測試移到獨立的測試執行檔。
2. `--test-threads=1` 只繞過測試內「同行程子行程被看成外部 holder」的問題。產品的鎖後 holder 重掃只排除自身 pid，而 daemon 確實會 spawn 子行程（`sw-pal/src/sysenv/posix.rs`、`process_tunnel/posix.rs`）。若 spawn 與 attach 並行，是否也會出現 `Held([自身子行程])`？這點本審未驗證，也沒有具體重現；建議與 Python `probe_holders` 的行為對照確認。
