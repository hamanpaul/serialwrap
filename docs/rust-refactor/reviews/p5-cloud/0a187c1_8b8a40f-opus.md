**發現：**

1. [Medium] `crates/sw-core/tests/lease_selftest.rs:938`、`:1255` — 這兩行直接使用 `env!("CARGO_MANIFEST_DIR")`，觸發 `check_cfg_boundary.py` 的 `test-data-path` 規則（只允許出現在 `tests/common/mod.rs`）。結果是計畫 Global Constraints 規定的必跑 gate 由綠轉紅，而 commit 訊息的驗證清單也沒有列這一項。
   - **修法：** 在 lease_selftest.rs 加 `mod common;`，兩處改用 `common::repo_path("contracts/golden/selftest_refused.json")`（`crates/sw-core/tests/common/mod.rs:7` 已有這個函式），再重跑腳本確認 exit 0。

2. [Medium] `crates/sw-core/src/op_runner.rs:582-586` 與 `session_core.rs:3893` — 命令逾時後送救援鍵，若救援鍵被 Frozen、StaleEpoch、Cancelled 以外的原因拒絕（例如 `Flash`、`WalUnhealthy`），Rust 回 `OpOutcome::Error`，`finish_command` 再把它映射成 `{ok:false, error_code:"SEND_FAILED"}`，而且不寫 META。
   - **Python 的實際路徑：** `_recover_after_failure` 遇到這類原因會 `raise` TxIncompleteError → `execute_command` 捕捉 → `_map_aborted_result(cmd_id, exc)`。這時 `tx_account(cmd_id)` 已記入命令本身送出的 bytes（例如 `sleep 20\n` 是 9 bytes），所以 confirmed > 0。
   - **Python 結果：** WAL 寫 META `{"event":"command_aborted_in_flight","confirmed_tx_bytes":9,"tx_outcome":"partial"}`，命令回 `{ok:false, error_code:"COMMAND_ABORTED_IN_FLIGHT"}`。
   - **重現：** READY 狀態下送 `sleep 20`（timeout 1 s），在送 CTRL_C 前把 fence 設成 `wal_unhealthy=true` 或 `flash_mode=Flashing`。
   - 3893 行的註解「→ SEND_FAILED」不正確。
   - **修法：** 命令路徑上，救援鍵遇到其他拒絕時，OpRunner 回 `CommandResult(map_send_failure(ctx, &report, 1, cmd_id))`，但 confirmed 要改用該命令累計已確認的 TX bytes（不是救援鍵本身的），`tx_outcome` 依 Python 規則（救援鍵 not_submitted → `"partial"`）。READY recover 路徑（cmd_id 為空）維持 `Error`，這部分 #34 已覆蓋。另新增 `recover_key_other_reject_in_command_maps_aborted_in_flight` 測試，斷言 META 內容與回碼。

3. [Medium] `session_core.rs:4395-4397`、`:3999-4001`、`:3124`、`:3435`、`:700` — 「Slice 2.1 單一前景槽」帶來幾個對外可見、但未登記的差異：
   - self-test 在命令執行中被呼叫：Rust 回 `{ok:false, error_code:"SESSION_BUSY", selector}`，Python 照送 nonce probe 並回 OK 或 TARGET_UNRESPONSIVE。
   - 同一個 lease 有兩個並行的 `interactive_send`：第二個 Rust 回 SESSION_BUSY，Python 兩個都寫出。
   - self-test probe、READY recover、interactive send 進行中：`session.public` 的 `foreground_busy` 在 Rust 是 true，Python 是 false（Python 只有命令與檔案傳輸會設這個旗標）。
   - 同樣這三種操作進行中，Rust 的 agent log 不寫入 RX，Python 會寫。

   parity-amendments #58 只把「READY recover 被前景槽擋住」排到 P8-T5 以 ALIGN-TO-PYTHON 處理，**self-test、interactive_send、`foreground_busy`、agent log 這四項在 parity-amendments 與 behavior_changes 裡都沒有登記**。
   - **修法：** 至少要做到：`capture_rx` 與 public dict 改用「目前前景 op 是否為命令」判斷（新增欄位 `foreground_is_command`），不要用 `foreground.is_some()`；self-test 與 interactive_send 的前景忙時拒絕，要不是改成可並行，就是登記一個 SC 條目並取得擁有者裁決，同時在計畫 Task 14 註明「T14 暫行、對齊目標見 #58／P8-T5」。

4. [Medium] `session_core.rs:307`、`:3377-3393` — background capture 的 64 筆上限放在每個 `SessionCore` 各自計算，Python 的 `SessionManager._background` 是整個 manager 共用，`_evict_background_locked` 依全域 `created_at` 淘汰。
   - **輸入：** COM0 與 COM1 各完成 40 筆 bg 命令。
   - **預期（Python）：** 總數維持 64，最舊的 16 筆已結束 capture 被淘汰，對它們做 `result_tail` 回 `CMD_NOT_FOUND`。
   - **實際（Rust）：** 80 筆全部保留，照常回 chunks。這也違反 §5.4 把 `BG_CAPTURE_MAX_COUNT=64` 當成 daemon 整體上限的意思。
   - **修法：** 把 capture 的登錄與淘汰移到全域共享的 `BackgroundRegistry`（以 `Arc<Mutex<>>` 經 deps 注入，淘汰時回呼擁有者 session 移除 `background_cmd_ids`），或在計畫中明確要求 T16 承接並補一個兩 session 合計 65 筆的測試。

5. [Medium] `session_core.rs:3960-3990` — 裝置在、bridge 尚未開成（ATTACHING，`pending_attach` 或 `open_real_path` 已有值）時呼叫 `session.recover`，Rust 回 `{ok:false, error_code:"SESSION_NOT_READY", session}`。Python `recover_session` 在 `bridge is None and by_id in self._devices` 時一律回 `{ok:true, recovering:false, action:"REATTACH", session}`（並重新 `_spawn_attach`）。
   - **修法：** attach 已在進行中時，不重複發 `OpenBridge`，但仍回 REATTACH 的 ok payload（`set_last_error(None)`、state 設 ATTACHING）；補測試 `recover_during_pending_attach_returns_reattach`。

6. [Medium] `session_core.rs:4328`、`:4519`、`:4528` — self-test 的 OK、ATTACHED 子分類、PASSTHROUGH、VTTY_STALE 各分支，`attached_vtty` 一律是 null。Python 用的是 `bridge.snapshot()["vtty"]`，POSIX 上是哨兵 PTY 路徑，例如 `"/dev/pts/7"`；每次 OK 結果的值都不同於 Python。core 自己拿不到 vtty，T16 也無法在不後處理的情況下補上。
   - **修法：** 在 `SelfTestProbes` 加一個 `vtty_path: Option<Arc<dyn Fn()->Option<String>>>`，各分支填入回傳值；補一個注入路徑後斷言 `attached_vtty` 等於該路徑的測試。

7. [Low] `crates/sw-core/tests/command_exec.rs:783` — `assert_eq!(h.dev.os_submits(), h.dev.os_submits())` 是恆真斷言，#55 的 `reboot_not_submitted_does_not_arm_quiet_e2e` 實際沒有驗證零 OS 提交。
   - **修法：** 在 `wait_paused` 之後先記下 `let submits = h.dev.os_submits();`，最後斷言 `h.dev.os_submits() == submits`。

8. [Low] `session_core.rs:2463` — `LeaseExpiry` timer 用 `now >= deadline` 就關閉 lease，Python 的 tick 與 `expired()` 都是嚴格大於（`now - last > timeout`）。剛好在邊界的那一刻，Rust 已經 tombstone，Python 仍是 active。
   - **修法：** 改成 `now > deadline`，或直接用 `lease.expired(now)`。

9. [Low] `session_core.rs:3051` — `interactive_open` 帶 `command` 時若前景忙，Rust 直接回 `ok:true` 而**完全不送出 command**，Python 一律送出。
   - **修法：** 前景忙時回 `SESSION_BUSY`（與 READY 分支一致），或排入佇列在前景結束後送出；不要默默丟棄。

10. [Low] `op_runner.rs:160` — base64 編碼遇到非 ASCII 時的例外訊息與 Python 不同。Python 是 `'ascii' codec can't encode character '\xe9' in position 0: ordinal not in range(128)`，Rust 是固定的 `...encode characters: ordinal...`，EXCEPTION framing 的 message 因此不一致。
    - **修法：** 照 Python `UnicodeEncodeError.__str__` 組字串（含第一個非 ASCII 字元的 `\x`／`\u` 表示與 position，連續多個時用 `characters in position a-b`）。

11. [Low] `crates/sw-core/tests/lease_selftest.rs:1333` — `selftest_probe_drain_race_golden` 只斷言 `committed + refused == iterations`。commit 說兩個分支都有出現，但測試沒有保證；若競態退化成只剩一種結果，測試仍會綠。
    - **修法：** 加上 `assert!(committed > 0 && refused > 0)`（或在迭代數不足時明確標示證據不足）。

12. [Low] `session_core.rs:3289-3297` — `mode=interactive` 的命令在已有 agent lease 時直接 `open_lease` 覆蓋，舊 id 之後查詢回 `INTERACTIVE_NOT_FOUND`。Python 的舊 lease 仍留在 `_interactive` 且狀態是 active：`status` 回 ok:true，`send` 因 fence `lease` 被拒而回 `INTERACTIVE_EXPIRED`。
    - **修法：** 被覆蓋的舊 lease 依 Python 語意保留可查詢的終態（至少 send 回 `INTERACTIVE_EXPIRED`），並補測試。
