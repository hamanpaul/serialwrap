### 91109e7 feat(rust-event): 承接事件 dispatcher 子程序池

1. **[Medium] `crates/sw-core/src/event_engine/dispatcher.rs:188` — 超大 timeout 會殺死 worker，並永久占住併發名額 — 確切修法：**

   合法規則輸入 `timeout_ms: 1000000000000000000000000000000`、`handler.exec:["/bin/true"]`，會被 `Rule::timeout()` 轉成 `Duration::MAX`。原生 spawner 在 `handler_posix.rs:193` 執行 `start + spec.timeout` 時溢位 panic；`run_handler` 因而跳過 `release()`，worker 也直接結束。不同規則重複觸發可耗盡全部 8 個 worker／名額，之後持續回報 `per_daemon_saturated`。

### 0722f75 feat(rust-event): 接線 reader observer、BridgeQueries 與 Event Engine 啟停

3. **[Medium] `crates/sw-core/src/session_core.rs:740` — interactive send 被誤分類為前景命令輸出 — 確切修法：**

   `interactive_open(command=...)`／`interactive_send` 將 `PendingOp::InteractiveOpen`／`InteractiveSend` 放進 `self.foreground`；這裡卻以 `self.foreground.is_some()` 發布事件分類旗標。

   具體情境：沒有前景 command，interactive send 的 TX 尚未完成時收到 `hit\n`。Python `active_cmd_id_for()` 回 `None`，因此 `spontaneous` 規則應觸發、`command_output` 不應觸發；Rust 回 `"foreground"`，兩者結果相反。Python 實際方法的記憶體探針已確認此預期。

   應改用既有 `self.foreground_busy()` 發布，與公開 session／capture 的判準一致；新增阻塞 interactive TX 期間注入 RX、同時驗證兩種 scope 的整合測試。

### 397a473 feat(rust-capture): agent log 改由 reader 端寫入並對齊 Python 回應

4. **[Medium] `crates/sw-core/src/session_core.rs:4356` — 首次成功 log_start 回應仍帶 `session.capture:null` — 確切修法：**

   未啟動 capture 時呼叫 `session.log_start`：此處先用 `self.session_dict(now)` 組好回應，下一行才設定 `self.log_capture`。所以頂層已有 `capture_id`／`log_path`，巢狀 `session.capture` 卻仍是 `null`。

   Python `log_start` 先設定 `session.active_capture`，再產生公開快照；記憶體實跑確認首次回應已有相同 capture ID、`status:"active"` 及零計數。這與既有報告的「後續計數恆為零」是不同問題。

   應先安裝 `self.log_capture` 再組回應；新增首次成功回應的 actor 測試，斷言巢狀 capture 非空且 ID／路徑與頂層一致。現有 golden 測試直接借用 golden 的 session，無法抓到此錯誤。
