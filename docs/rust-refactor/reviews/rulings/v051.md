## 編排者裁決（2026-11-23）：p277 在 hold 下的 windows-task 顯式 start

拆分器回報作者的測試 `mgmt_service.rs:103-115` 規定 switch hold 時仍要 `/Run`，而 on-demand 的 journal 防護是不啟動、保留 `SOCKET_ERROR`，兩者無法直接套用，要求裁決。裁決如下：

1. **`install-journal.json` 存在時（更新或回滾進行中、或中斷）視同 hold**，和 `autostart-hold.json` 走同一個 hold 分支：不得 `/ENABLE`，其餘沿用作者測試已定的 hold 行為（只 `/Run`，回應與 exit code 不變）。不新增錯誤碼，也不新增 phase。
   - 理由：hold 期間排程工作處於停用狀態，`/Run` 會像 issue 276 的現象一樣失敗，daemon 不會被提早啟動。原本的缺陷是漏判 journal，導致誤送 `/ENABLE`，讓 `/Run` 成功。
2. 偵測到 hold 時，比照 on-demand 防護的文字，在 stderr 補一段說明（例如「更新／回滾進行中」或「監管模式切換進行中」，並提示待 `serialwrap setup` 完成或依指示恢復）。JSON 回應的欄位不變。
3. 查 hold 與 `/ENABLE`／`/Run` 要在生命週期交易使用的同一個鎖下進行（既有 `autostart_lock` 等），避免檢查之後才建立 hold 的 TOCTOU。
4. 作者既有的 4 支測試維持原樣通過，不得修改。新增 journal hold（`service start` 與 `daemon start` 兩個入口）及受控交錯的測試。
5. 停用中的排程工作被 `/Run` 時，在 Windows 實機上的實際結果，待 Windows 實機驗證。

## 編排者裁決（2026-11-23）：ci-thin DF-23「沒有新的 attach 嘗試」的偵測方式

## 編排者裁決（2026-11-23）：ci-thin DF-23 holder 檢查改為「不得出現新的 holder fd」

ci-thin-i2-L2 實測發現：Python 基線在核准的 DETACHED 終態下，**仍持有目標 tty**（例如 fd `9->/dev/pts/12`）。上一則裁決要求「觀察期內只要持有就失敗」，Python 分支因此 0／20，與「Python 停在 DETACHED、不自動重試」這個判準互相衝突。

- **裁決**：holder 檢查要偵測的是「**新的** attach 嘗試」，不是「有沒有持有」。改成以下判準：
  1. 觀察期開始時（建立 baseline 的那一次取樣），記下 daemon 持有目標 tty 的 fd 集合，作為 baseline holder 集合，可以是空集合。
  2. 觀察期間每次取樣，持有目標 tty 的 fd 都必須是 baseline 集合的子集合。**出現任何 baseline 以外的 fd，就判為新的 attach 嘗試**，測試失敗。
  3. baseline 中的 fd 一旦消失，就不得再出現。消失後又出現，視同重新開啟，測試失敗。這是為了抓到「關閉後以相同 fd 編號重開」的情況。
  4. 已知限制寫進 docstring：無法分辨「同一 fd 一直開著」與「在兩次取樣之間關閉後又以相同編號重開」。後者由第 3 點盡量覆蓋，其餘列為限制。
- **Python 在 DETACHED 下仍持有 tty**：這是 Python 凍結基線的既有行為（OD-111），照實在測試 docstring 記錄。不改 Python，也不把它當成本測試的失敗。Rust 分支與 §11.3-4 的 handle 時序斷言一字不改。
- **權限錯誤（V051-4ff31b4-1）**：fd 路徑的解析要使用會傳出錯誤的方式，例如 strict realpath。只有確認 fd 已消失的 `ENOENT` 可以放行，其他錯誤（含 `EACCES`）一律讓測試失敗。補一支受控交錯測試：第一次 `readlink` 成功、後續解析回 `EACCES`。
- **突變證明**：保留「觀察期內重新開啟目標 tty（新 fd）→ 轉紅」；另加一支「baseline fd 關閉後重開」的突變，確認也會轉紅。
