## 編排者裁決（2026-11-11）：wp510r R3 的期限時鐘與 drain_timeout_epoch（SPEC-GAP 2、3）

**SPEC-GAP 2：release／bind 期限在測試 rig 中的時鐘。** R3 把 release／bind 的等待收進 actor 後，actor 計時器在 ManagerRig／ServiceRig 用 FakeClock，測試不推進時鐘就不會到期；現行凍結的時間節點（daemon #66、#67、#69、#70、#71、#97；core #39、#41、#42、#50、#53、#57）量的是實際耗時。實作者在 c5f9b38a 採用：release 的 RPC 執行緒以實時在 RPC 進入時起算首次期限（+3 s），期限到仍未收到回覆就通知 actor「首次期限已到」（`ReleaseDeadlineElapsed`）。

裁決：**採用這個做法**，並延伸到帳本路徑的 ReleaseWait 與 BindWait。依據：Python 的 release／bind 本來就是 RPC 執行緒以實時等待期限（py:3117-3124、3192-3204、3695-3710）；正式 daemon 的 actor 時鐘也是實時，行為不變；凍結節點不必改。條件：
1. 首次期限只在首次 release 時決定一次，記在被等待的對象上（帳本紀錄或 retired drain），之後的 release 沿用，不得以各自的 RPC 進入時間重算（WP2-2）。
2. 通知必須帶被等待對象的身分（token／epoch／stop_id 與期限），actor 只結算目前仍在等的那一筆；重複或過期的通知不產生效果。
3. actor 自己的期限計時器保留，FakeClock 推進的測試照常由它收尾；兩者誰先到都只結算一次。
4. 補回歸：首次期限由第一次 release 決定、第二次 release 共用；過期通知對新的等待無效；actor 計時器與 RPC 通知同時到時只回覆一次。

**SPEC-GAP 3：「開埠在途直接轉自身 bridge 排空」收斂後的 `drain_timeout_epoch`。** 凍結節點 `core::drain_release::release_during_pending_open_reply_is_stalled_until_close_receipt` 要求保留 epoch；P8-c4913ae-1 的預期是 false/null。

裁決：**依 Python 各路徑的語意**。Python 的 `_complete_drain`（自身 bridge 排空）成功時只清 `drain_stalled`，不清 `drain_timeout_epoch`（py:2884-2913）；`_finish_attach_op`（attach 作業）成功時兩欄都清（py:4345-4350）。所以自身 bridge 排空路徑保留 epoch，凍結節點不改；經在途作業或帳本紀錄收尾的路徑兩欄都清。P8-c4913ae-1 的 false/null 預期只套用在後者，回歸測試照此區分。

編排者查證 `.github/workflows/release.yml` 目前無法產出 0.5.0 RC：tag 必須等於 `v${VERSION}`（第 44～53 行），`v0.5.0-rc.N` 會被擋，release 也不會標 pre-release；Linux bundle 未帶 `--stage 2`（第 201 行），會建成 Stage 1（Python daemon）；CI 會重建執行檔，與 gate 測過的不是同一份。編排者決定（併入收尾線，定候選版之前完成）：

1. RC 為 GitHub pre-release `v0.5.0-rc.N`，資產是 **gate 共用證據中測過的同一份** Linux 與 Windows Stage 2 bundle，加上 `SHA256SUMS` 與試裝說明；`VERSION` 維持 `0.5.0`（OD-100）。release workflow 對 `v<VERSION>-rc.N` tag 只做驗證（tag 與 `VERSION` 的關係、資產 SHA256、bundle manifest 的 `git_revision` 與 stage），不重建、不覆蓋資產。

## 編排者裁決（2026-11-17）：`SERIALWRAP_TEST_SYSTEM_CONFIG_PATH` 的守衛差異列為已知差異

線 A 第 10 項核對 4 個放行鉤子的守衛時發現：Python `sw_core/constants.py:35` 在任何實例都直接採用 `SERIALWRAP_TEST_SYSTEM_CONFIG_PATH`，Rust 只在隔離實例採用、非隔離實例忽略。Rust 比 Python 嚴格，正式實例不會有人設這個測試變數，且嚴格的一方較安全。裁決：列為已知差異，不改 Python 基線（OD-75），也不放寬 Rust；出口報告與已知差異清單一併列出。前一則裁決「每一個在 Rust 都有與 Python 相同的守衛」對這一個鉤子的要求，改為「Rust 的守衛不得比 Python 寬鬆」。

## 編排者裁決（2026-11-18）：撤回「SYSTEM_CONFIG_PATH 守衛差異」，改為與 Python 相同

合併線 A 與線 C 時發現衝突：線 C 為 parity #2（`sysenv_test_system_config_path_overrides`）把系統設定路徑改由 `sw-proto` 的 `RuntimePaths.system_config_path` 計算，任何實例只要設定 `SERIALWRAP_TEST_SYSTEM_CONFIG_PATH` 即採用（與 Python `sw_core/constants.py:35` 相同；Python 的 CLI 與 daemon 共用此常數，所以 Rust 的 CLI 與 daemon 也都讀它）。線 A 第 10 項則在 daemon 舊函式加了「僅隔離實例採用」的守衛。

裁決：

## 編排者裁決（2026-11-19）：PR #278 hosted CI 的平台標記修正

PR #278（`feature/rust-refactor-p8` → main）第一次在 GitHub hosted runner 跑完整 CI，`pytest-windows`（`-m "core_portable or windows_native"`，hosted `windows-latest`，無 Rust 執行檔、`bash` 指向未安裝 distro 的 WSL 啟動器）42 支失敗。可攜性問題已修（換行、路徑分隔、含冒號的集合目錄名、`/tmp` 假設等）；以下三點需要裁決：

1. **17 個節點的平台 marker 由 `core_portable` 改為 `posix_only`**：16 個 gate 工具測試實際以 `bash` 執行 `scripts/rust/*.sh`（`tests/test_gate_shared_evidence.py` 的 dry-run／driver 類 7 支、`tests/test_s22_gate_check.py` 7 支、`tests/test_shell_local_same_line.py::test_bash_nounset_same_statement_reference_exits_with_error`、`tests/test_p7_gate_report.py::test_required_rows_complete`），以及 `tests/test_rust_goldens_fresh.py::test_golden_is_fresh[gen_allowlist_unreadable_config.py-allowlist_unreadable_config.tsv]`（generator 用 `os.geteuid`、`chmod`、`/usr/bin/setpriv`）。`core_portable` 的定義是「Linux 與 Windows 都必跑」，這些節點依賴 POSIX，標記本來就錯。它們只鎖在 Linux 集合（`p7_gate:python3-m-pytest-q-tests`、`s21_gate:pytest_full`），`posix_only` 在 Linux 照常收集，鎖定集合不變，不屬任何 Windows 鎖定集合。
2. **`tests/contract_blackbox/slice21/test_windows_nocom.py` 的 `test_deferred_methods_windows` 與 `test_wal_share_delete_while_running` 加 `rust_only`**（兩者在 `s0_win_pytest` windows 集合）：前者驗 Rust 延後方法回 `METHOD_NOT_FOUND`（Slice 2.1 契約，Python 回 `SESSION_NOT_READY`）；後者以 `session.bind` 觸發 WAL 寫入再驗 Windows 分享刪除，Python 基線在無 COM 時不會因此建立 WAL，該節點從未在 Windows 以 Python 通過。兩者都是 Rust B 輪才有意義的斷言，Python A 輪依既有 `rust_only` 規則不執行。待辦（ledger）：為 `test_wal_share_delete_while_running` 定義 Python 基線也成立的無 COM WAL 觸發方式，恢復 A 輪覆蓋。
3. **`test_second_daemon_exit_2` 比對前正規化換行**（`\r\n` → `\n`）可接受：Python 在 Windows 文字模式寫 stderr 的 CRLF 是平台慣例，不屬訊息契約；訊息內容與 exit code 2 的斷言不變。
