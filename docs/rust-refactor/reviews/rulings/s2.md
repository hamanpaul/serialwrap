## 編排者裁決（2026-11-11）：wp510r R3 的期限時鐘與 drain_timeout_epoch（SPEC-GAP 2、3）

**SPEC-GAP 2：release／bind 期限在測試 rig 中的時鐘。** R3 把 release／bind 的等待收進 actor 後，actor 計時器在 ManagerRig／ServiceRig 用 FakeClock，測試不推進時鐘就不會到期；現行凍結的時間節點（daemon #66、#67、#69、#70、#71、#97；core #39、#41、#42、#50、#53、#57）量的是實際耗時。實作者在 c5f9b38a 採用：release 的 RPC 執行緒以實時在 RPC 進入時起算首次期限（+3 s），期限到仍未收到回覆就通知 actor「首次期限已到」（`ReleaseDeadlineElapsed`）。

裁決：**採用這個做法**，並延伸到帳本路徑的 ReleaseWait 與 BindWait。依據：Python 的 release／bind 本來就是 RPC 執行緒以實時等待期限（py:3117-3124、3192-3204、3695-3710）；正式 daemon 的 actor 時鐘也是實時，行為不變；凍結節點不必改。條件：
1. 首次期限只在首次 release 時決定一次，記在被等待的對象上（帳本紀錄或 retired drain），之後的 release 沿用，不得以各自的 RPC 進入時間重算（WP2-2）。
2. 通知必須帶被等待對象的身分（token／epoch／stop_id 與期限），actor 只結算目前仍在等的那一筆；重複或過期的通知不產生效果。
3. actor 自己的期限計時器保留，FakeClock 推進的測試照常由它收尾；兩者誰先到都只結算一次。
4. 補回歸：首次期限由第一次 release 決定、第二次 release 共用；過期通知對新的等待無效；actor 計時器與 RPC 通知同時到時只回覆一次。

**SPEC-GAP 3：「開埠在途直接轉自身 bridge 排空」收斂後的 `drain_timeout_epoch`。** 凍結節點 `core::drain_release::release_during_pending_open_reply_is_stalled_until_close_receipt` 要求保留 epoch；P8-c4913ae-1 的預期是 false/null。

裁決：**依 Python 各路徑的語意**。Python 的 `_complete_drain`（自身 bridge 排空）成功時只清 `drain_stalled`，不清 `drain_timeout_epoch`（py:2884-2913）；`_finish_attach_op`（attach 作業）成功時兩欄都清（py:4345-4350）。所以自身 bridge 排空路徑保留 epoch，凍結節點不改；經在途作業或帳本紀錄收尾的路徑兩欄都清。P8-c4913ae-1 的 false/null 預期只套用在後者，回歸測試照此區分。
