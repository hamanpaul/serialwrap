## OD-83（擁有者，2026-11-09）：windows-task 崩潰重啟（SC-24）

2026-11-09 依 OD-28 在本機 Windows 實跑 P8 Task 13：強制結束 daemon 後 daemon 以 exit 1 結束，Task Scheduler 記為正常完成，`RestartOnFailure`（PT1M／999）只對排程器層級的啟動失敗重試，150 s 內沒有重新啟動。`s24-sup-wintask-runtime` 契約中「強制終止 daemon 後 150 s 內由排程重新拉起新 pid」不成立。windows-task 是 Rust-only 監管模式（`05-stage1b-rust-cli-mgmt.md:570`），沒有 Python 基線。

擁有者裁決：**A＋B**。
- **0.5.0（Stage 2）採 A**：調整 SC-24 預期。windows-task 提供登入自動啟動與有序停止，**不提供崩潰自動重啟**，列為已知限制（0.4.1 release notes 已登記）。`s24-sup-wintask-runtime` 的契約與 `wintask_runtime.rs` 改為驗證：強制終止後排程工作不會自動重新拉起（記錄平台實際行為），以 `service start` 可恢復新 pid，之後的隔離防線、有序停止與 WAL 斷言照舊。工作 XML 維持現狀（`RestartOnFailure` 仍可涵蓋啟動失敗）。凍結案例屬性變更走正規修訂鏈，decision 為 OD-83。
- **長期採 B**：Windows 的崩潰重啟行為要與 Linux 對齊（Linux systemd-user unit `Restart=on-failure` 會自動重啟）。0.5.0 之後實作（候選做法：工作 XML 加重複觸發搭配 `IgnoreNew`），屆時再把上述「不會自動重新拉起」的斷言改為「在期限內重新拉起」，並重新以 Windows 原生實跑驗證（需 Defender 排除，見 T13 runbook）。
