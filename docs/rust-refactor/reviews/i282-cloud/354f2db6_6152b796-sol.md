## B 新發現

### I282-6152b79-1 [Medium] regression/serialwrap_regression/cases/f07_file_transfer.py:634 — 停機前讀不到在途半行 WAL

正式 `OpTransferPort` 將 echo-paced slices 以 `AggregateOp::Append` 聚合，直到 `finish()` 或 writer 收尾才寫入 WAL（`crates/sw-core/src/tx_writer.rs:1114`、`file_transfer/op_port.rs:208`）。

具體情境：兩個 chunk 完成，第三個 chunk 已送 64 bytes、正在等待被關閉的 echo。此時 WAL 只有前兩個完整 chunk，判定持續回 `False`；正常 echo timeout 後傳輸結束，案例走 `push_not_observed_inflight` 的 **SKIP**，未在要求的切點送 SIGTERM。此項為正式呼叫路徑的靜態證據。

**確切修法：**改以獨立 UART／bridge byte 觀測確認半行，再觸發 SIGTERM；補上經正式 echo-paced 路徑、停用停機收尾必回 FAIL 的驗證。

### I282-6152b79-2 [Medium] regression/serialwrap_regression/cases/f07_file_transfer.py:418 — 半行前綴與正式命令不符

判定要求 `printf '%s' '`，但 Python `_chunk_command()` 與 Rust `templates::chunk_command()` 都使用 `shlex.quote(encoded)`。非空 base64 的字元全部屬安全字元，因此正式本文不加單引號。

以 Python 基線實際產生 chunk，提供兩個完整 chunk、echo-off marker、busy 狀態及第三行前 64 bytes，實測得到：

```text
baseline chunk prefix: b"printf '%s' AAECAwQFBgcICQoLDA0O"
observed=False
```

即使解決 B-1，這項仍會阻止有效切點成立。

**確切修法：**辨識正式的未加引號 base64 前綴；測試資料改由正式樣板產生，保留完整行拒絕斷言。

### I282-6152b79-3 [Medium] regression/serialwrap_regression/guards.py:154 — 無關行程的非 ASCII 名稱會使停機驗收失敗

掃描在判斷 pgrp 前，以 ASCII 解碼整份 `/proc/<pid>/stat`；Linux 行程名稱可以包含非 ASCII bytes。

以隔離行程設定名稱「測試行程」，查詢不相干 pgid，實測仍拋出：

```text
UnicodeDecodeError: 'ascii' codec can't decode byte 0xe6 ...
```

因此 daemon 即使正常退出，主機上任何此類行程都可能使 `wait_for_exit()` 失敗，案例誤報 `daemon_stop_timeout`。

**確切修法：**使用 `read_bytes()`，從最後一個 `)` 後解析 state／pgrp；補上非 ASCII 名稱且不同群組的測試。

定向測試：`tests/test_regression_harness.py` **22 passed**；使用 `--noconftest -p no:cacheprovider` 避免載入 live guard，並停用 bytecode 寫入。未跑完整 pytest、Docker／bundle 或真機測試；未接觸 production daemon、正式設定／狀態或實體 UART。工作樹保持乾淨。
