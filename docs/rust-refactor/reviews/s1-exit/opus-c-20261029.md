## 發現

### S1X-c-1 [Medium] crates/sw-cli/src/rollback.rs:1260 — 更新／回滾一律以 `local_default_endpoint` 探測舊 daemon，systemd-system（`/run/serialwrap/serialwrapd.sock`）的 daemon 完全沒被偵測：flash／busy 安全檢查被跳過、舊 daemon 沒停、新版沒啟動，報告卻是 `ok:true`

**問題**

`execute_change_with_restore` 以 `endpoint = local_default_endpoint(ctx)` 作為 `safety_check`、`stop_supervisor`、`confirm_released`、`start_and_verify` 共用的 endpoint；POSIX 上它就是使用者的 `$XDG_RUNTIME_DIR/serialwrap/serialwrapd.sock`（`endpoint_resolve.rs:71-85`），不讀 `config.yaml` 的 `socket_path`，也不依 `supervision_mode` 換成 systemd-system 的 canonical socket。systemd-system unit 的 daemon 跑在 `--socket /run/serialwrap/serialwrapd.sock`（`setup_cmd.rs:802`），因此：

- `safety_check`：`health.ping` 打到使用者 socket 沒有回應，就改掃 `/proc`；但 `matching_daemons`（`rollback.rs:225`）只保留 `--socket` 等於該 endpoint 的實例，`/run/serialwrap/...` 的 daemon 被濾掉 → 回傳 `daemon=None`。結果是 `mcu.status`（flash）與 `session.list`（file transfer／interactive／recovering）的拒絕條件**一個都沒檢查**。這違反規格 §12.1 第 2、3 步（「檢查 Flash、FileTransfer……不符合交接條件時拒絕更新」「再要求 daemon 安全停止」）。
- `stop_supervisor` 因 `daemon.is_none()` 走 `ensure_released_or_rehandoff(…, 使用者 socket, …)`，判定「已釋放」，從未對該 daemon 送 `daemon.handoff_stop` 或停止 systemd-system service。
- `start_and_verify` 以 `original.daemon.is_some()==false` 判為 `daemon_was_not_running`，不啟動也不驗證新版；`current-release.json` 已切到新版。舊版 daemon 繼續執行舊程式碼，直到下次重啟才換新版；事後 `doctor` 的 `version_pairing` 會失敗。報告本身卻是 `ok:true`，使用者無從得知。
- 首次安裝（0.3.2 pipx → 0.4.0，`op="install"`）也用同一個 endpoint 做 safety_check，舊 systemd-system daemon 一樣偵測不到：既不會照 release 計畫 §5.1 回 `METHOD_NOT_FOUND` fail-closed，也不會走 OD-48 的舊版停止路徑；而是直接進 reconcile 換掉 unit 檔，舊 daemon 繼續跑。OD-48 只裁決「偵測到不支援 handoff 的舊 daemon 時怎麼辦」，不包含這個偵測缺口。
- 同一根因也可能影響 `run_supervision_switch`（`rollback.rs:3552` 同樣用 `local_default_endpoint`）。這點未另行重現，只列為修正時要一併檢查的位置。

在不同 endpoint 時 two-reader 不會發生（舊 daemon 沒被停，新版也沒被啟動），所以不列 High。但「安全檢查被跳過＋更新宣稱成功卻沒換版」是有具體輸入、輸出的錯誤，列為 Medium。

**確切修法**

1. 新增 `fn instance_endpoint(ctx, mode: &SupervisionMode, config: &RuntimeConfig) -> String`：`SystemdSystem` → `/run/serialwrap/serialwrapd.sock`；Windows 模式 → 現行 `local_default_endpoint`；其餘依序取 config 的 `socket_path`（可連者優先，對齊 #108 #2 的 fallback 規則）、再退回 `local_default_endpoint`。`execute_change_with_restore`（`rollback.rs:1260`）與 `run_supervision_switch`（`rollback.rs:3552`）改用這個 endpoint，且 `old_mode` 與 `target_mode` 各自取一次（停舊用舊模式的 endpoint，啟新／驗證用目標模式的 endpoint）。
2. `safety_check` 在 ping 不通、改掃 `/proc` 時，若找到任何 `--socket` 不等於該 endpoint 的 `serialwrapd` 實例，應 fail-closed 回 `DEVICE_STILL_HELD`（附 pids 與其 socket），不要靜默濾掉。這可以同時擋住 on-demand 自訂 socket 之類的其他漏網情境。
3. 補回歸測試：用上述 `with_procs(socket=Some("/run/serialwrap/serialwrapd.sock"))`＋flashing，分別跑 `setup --system --with-sudo` 的 update 與 first-install，斷言 `FLASHING_BUSY`／`update_safety_check`，且 `current-release.json` 不變。現行程式下兩案都會紅。

### S1X-c-2 [Medium] docs/rust-refactor/release-0.4.0-plan.md:67 — release notes 升級步驟說 `bin/serialwrap setup`「沿用 config 的監管模式」，實際不加旗標時會依 0.3.2 規則自動改成 systemd-user（有 systemd 時），on-demand 使用者照做會被改成 systemd-user

**問題**

§5.1 步驟 2 寫「執行 `<bundle>/bin/serialwrap setup`（沿用 config 的監管模式；可加 `--user`／`--on-demand`）……config、profiles、state.json 不變」。但 `resolve_target_mode`（`setup_cmd.rs:696-721`）不讀 config：沒有旗標時，有 systemd 就選 `systemd-user`，否則選 `on-demand`。這和 0.3.2 `_resolve_target_mode` 逐字一致，所以程式行為本身是 1:1，不是缺陷；錯的是對外升級程序的說法。照文件操作的 on-demand 使用者（或 systemd-system 使用者，只要沒加 `--system`）會在升級時被切成 systemd-user：unit 被安裝並啟用、`loginctl enable-linger` 被執行，`config.yaml` 的 `supervision_mode` 也被改寫，與同一段「config 不變」的說法互相矛盾。`run_upgrade_container.py:231/250/365` 一律傳入明確的 `--user`／`--on-demand`，所以 Docker 升級驗證從未涵蓋文件描述的無旗標路徑。

- §5.1 步驟 2 改為：「執行 `<bundle>/bin/serialwrap setup` 並**明確指定目前的監管模式**（`--user`／`--system --with-sudo`／`--on-demand`）。不加旗標時與 0.3.2 相同，會自動選擇（有 systemd → systemd-user，否則 on-demand），可能改變現有模式與 `config.yaml`。」§7 release notes 的中英文段落同步加上這條提醒。

### S1X-c-3 [Low] crates/sw-cli/src/rollback.rs:41 — 正式二進位仍編入 `crash_if` 注入點與 `pub fn set_test_crash_point`／`set_test_hook`

只能由同一行程內的整合測試經 thread-local 觸發，沒有環境變數或 RPC 入口，因此沒有具體的外部失敗情境（release 二進位中可見 `injected process interruption at` 字串）。建議收在 `#[cfg(any(test, feature = "test-fakes"))]` 之後，非 test-fakes 版提供空實作。這與註解提到的 arch §2.1 cfg 邊界相容（允許 `feature = "test-fakes"`）。

### S1X-c-4 [Low] crates/sw-cli/src/setup_cmd.rs:1032 — `windows_task_definition` 固定 `register_held: false`，不理會 `ReconcileRequest.hold_target`

systemd 分支用 `same_mode || req.hold_target`；windows-task 分支則在首次安裝交易（`hold_target=true`）期間，就以 enabled 狀態註冊工作（只是不立即 `/Run`）。在 `start_and_verify` 之前，若剛好遇到登入觸發，工作可能被提前拉起。發生機率極低，又有後續的 handoff 檢查兜底，所以沒有具體失敗情境。建議改成 `register_held: same_mode || req.hold_target`，與 systemd 一致。

## 既有碼待辦（不計入結論）

- 無旗標的 `setup` 會自動選 systemd-user：這是 0.3.2 既有語意（`_resolve_target_mode`），Rust 照搬，本報告不列為缺陷，只在 S1X-c-2 要求修正文件。若擁有者希望「升級沿用 config 模式」，屬於 SC 層級的變更，要另立 OD。
- 失敗的首次安裝回退時，`restore_original` 不會還原 `materialize_assets` 寫出的工具與 skill 資產（`~/.local/share/serialwrap/...`）；profiles 有 backup 保護。目前沒有觀察到具體影響，可記入 low-backlog。
- `run-upgrade.sh` 預設以 `--version-override 0.4.0` 建 bundle，release 計畫 §2 則規定正式 bundle 不得使用 override。計畫 §4.1 已註明正式驗證要用 `--bundle` 指向 release bundle；建議腳本在 `--bundle` 未指定時於報告標記 `candidate_kind: version_override`，避免日後把開發 bundle 的報告誤當成前置條件 #3 的證據。
- 環境備註（不是產品缺陷）：在只允許 HTTPS 的 proxy 環境下，`upgrade.Dockerfile` 的 apt 走明文 HTTP 無法建置。若雲端審查要常態重跑，可考慮讓 Dockerfile 接受選用的 CA／https 來源 build-arg。

## 對裁決的異議（不計入結論）

- 無。OD-48 的實作驗收應涵蓋 S1X-c-1 的 systemd-system／非預設 socket 情境；否則「改走舊版停止路徑」在 systemd-system 模式下根本不會被觸發，因為舊 daemon 偵測不到。
