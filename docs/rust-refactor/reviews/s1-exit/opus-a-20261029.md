### S1X-a-1 [High] `sw_core/session_manager.py:6582` — `mode=interactive` 命令永遠送不到 UART，且遺留 agent lease

- **問題**：`_execute_command_inner` 的 interactive 分支以 `TxPermit(cmd_id, gen, "interactive")` 送命令。同一臨界區內 `_open_interactive_locked` 經 `_push_tx_gate`（`:726`）發佈的 `lease_owner` 是 `"interactive:<lease_id>"`。`uart_io._tx_reject_reason`（`uart_io.py:622-624`）要求 `permit.op_id == _gate_lease_owner`，因此必定回 `lease`，命令被拒，`execute_command` 映射為 `SEND_FAILED`。
- **對照**：同檔 `:7182`、`:7271`（interactive_open／send）都正確使用 `f"interactive:{id}"`，只有這一處用了 `cmd_id`。
- **失敗情境**：
  - `serialwrap cmd submit --selector COM0 --mode interactive "top"`：
    - 0.3.2 回 `{"ok":true,"execution_mode":"interactive",...}`，並寫出 `top\n`。
    - 0.4.0 回 `{"ok":false,"error_code":"SEND_FAILED"}`，UART 零寫入。
    - 剛開的 agent lease 沒有關閉，下一個命令得到 `SESSION_INTERACTIVE_BUSY`，直到 lease 逾時。
  - human line console（第二個以後的 console）輸入 `vim`／`top`／`less` 等，會經 `service._human_console_mode` 判為 `interactive`，走同一路徑，同樣送不出去。
  - 不在任何 BC／SC／DF 內；屬已有功能回歸。
- **重現**：真 `UARTBridge`＋FakePort，READY session 送 `mode=interactive`、`cmd="top"`：

  ```
  result: {'ok': False, 'error_code': 'SEND_FAILED'}
  writes: []
  reject reason: lease gate owner: interactive:4ffed4ba8a3d4508bb229fd53e1cc13d
  next cmd: {'ok': False, 'error_code': 'SESSION_INTERACTIVE_BUSY', 'interactive_session_id': '4ffed4ba…'}
  ```

  以下面的修法在暫存副本中重跑：`ok:True`，`writes: [b'top\n']`。
- **確切修法**：
  - `:6582` 改為 `TxPermit(f"interactive:{lease.interactive_id}", session.bridge_generation, "interactive", owner_gen=getattr(bridge, "owner_gen", 0))`。
  - 送出拋例外或被拒時關閉剛開的 lease。
  - 補回歸測試：真 `UARTBridge`＋FakePort 送非空 interactive 命令，斷言 bytes 寫出且 `ok:true`。現有 `test_interactive_mode_unchanged` 用的是空命令，`test_refine_ownership` 用的是不帶 permit 的替身，都測不到。

### S1X-a-2 [High] `sw_core/service.py:731-745` — `file.push`／`file.pull` 在 RECOVERING／FLASHING 的錯誤碼改變，未登記

- **問題**：`_resolve_session_id` 新增的 RECOVERING→`SESSION_RECOVERING`、FLASHING→`FLASHING_BUSY` 分支，也套用在 `file.push`／`file.pull`（`:1389`、`:1423` 以 `file_transfer=True` 呼叫同一函式）。
  - SC-01／SC-02 的 `compatibility_impact` 只核准 **CmdSubmit 與 InteractiveOpen**。
  - 規格 §5.3 表後明文：「表中未逐項列出的既有 query、cancel、capture、**file** 與管理命令，仍依第 9 章契約…承接」。
  - `contracts/error_codes.yaml` 把 file.* 列進這兩個碼的 scope，但 BC 登記沒有涵蓋。
- **失敗情境**：agent 在 session 恢復中或燒錄中呼叫 `file.push`，依 0.3.2 的 `SESSION_NOT_READY` 分支重試，結果收到未處理的新碼。
- **重現**：以替身 `_sessions` 讓 `get_session_state` 回指定 state，呼叫 `SerialwrapService._dispatch`：

  ```
  == base                                   == fr
  RECOVERING file.push SESSION_NOT_READY    RECOVERING file.push SESSION_RECOVERING
  RECOVERING file.pull SESSION_NOT_READY    RECOVERING file.pull SESSION_RECOVERING
  FLASHING   file.push SESSION_NOT_READY    FLASHING   file.push FLASHING_BUSY
  FLASHING   file.pull SESSION_NOT_READY    FLASHING   file.pull FLASHING_BUSY
  ```

  沒有任何測試釘住 file.* 在這兩個 state 的回碼。
- **確切修法**（二擇一）：
  - (a) 在 `_resolve_session_id` 以 `if not file_transfer:` 包住 RECOVERING／FLASHING 兩個分支，file.* 回到 `SESSION_NOT_READY`；`error_codes.yaml` 對應移除 file.* scope；補兩案回歸。
  - (b) 若要保留新碼，依收斂規則 §4 升級擁有者，擴充 SC-01／SC-02 的 `compatibility_impact` 涵蓋 file.*（改變規格語意，不得由實作者自行認定）。

### S1X-a-3 [High] `sw_core/session_manager.py:3315-3330` — 進行中 attach 時 `device attach` 回 `SESSION_RECOVERING`，0.3.2 回成功

- **問題**：`attach_device` 只要 `by_id` 在 `_attach_ops`／`_preopened_ports`／`_active_attach_ops`／`_attach_bridges` 任一表內，就回 `SESSION_RECOVERING`。`_attach_bridges` 在整段 probe／login 期間（最長 `timeout_s`）都持有 entry，這時沒有任何 drain、state 也是 ATTACHING。
  - SC-05 只新增 `DEVICE_STILL_HELD`／`DEVICE_NOT_PRESENT`。
  - SC-04 只涵蓋 drain 期間。
  - 「attach 進行中」這個觸發條件不在任何已核准列內。
- **失敗情境**：daemon 啟動後 bootstrap attach 尚在登入時，或第一次 `device attach` 回 ATTACHING 後立刻再呼叫一次：
  - 0.3.2 回 `{"ok":true,"session":{...,"state":"ATTACHING"}}`。
  - 0.4.0 回 `{"ok":false,"error_code":"SESSION_RECOVERING"}`，CLI exit 非 0，依碼分支的 agent 會誤判為恢復中。
- **重現**（FakePort 延遲登入，連續兩次 `attach_device`）：

  ```
  base: 2nd True None ATTACHING     final READY
  fr:   2nd False SESSION_RECOVERING ATTACHING     final READY
  ```
- **確切修法**：上述四表命中，但沒有 `_pending_drain`、不在 `_draining_by_ids`、沒有 release 請求、session 也不是 RELEASED 時，回 `{"ok":True,"session":session.to_public_dict()}`（與 0.3.2 相同）。`SESSION_RECOVERING` 只保留給 drain／release 進行中。補回歸測試。

### S1X-a-4 [Medium] `sw_core/session_manager.py:7975`／`:8087`（`file_push`／`file_pull`）＋`uart_io.py:620` — 傳輸中目標重開機時 `TxIncompleteError` 穿越 RPC 邊界，回 `EXCEPTION`

  - 例外最後落到 `rpc_posix.py:59` 的通用 handler，回 `{"ok":false,"error_code":"EXCEPTION","message":"tx incomplete: not_submitted 0/64 quiet"}`。

  - 不送 bytes 進 autoboot 倒數本身較安全，但對外結果改變且未登記。SC-04 的 approval_conditions 只涵蓋 system／probe TX，DF-19 只涵蓋 self-test。

  - 若選擇保留「傳輸中 quiet 即拒送」的新語意，須另登記 SC。

### S1X-a-5 [Medium] `sw_core/multi_open.py:217-220`（`daemon_process_alive`）— 主機上任何不帶 `--socket` 的 serialwrapd 都讓 setup／daemon restart 逾時失敗

- **問題**：舊 pid 未知（`pid=None`）時改走全行程掃描：
  - 只要掃到任一不帶 `--socket` 參數的 serialwrapd 就回 `None`；systemd-user unit 的 ExecStart 正是不帶 `--socket`（`setup_cmd.py:297`）。
  - 任一 cmdline 讀取失敗（例如 `hidepid`）也回 `None`。
  - `wait_old_daemon_gone`（`setup_cmd.py:264`）只接受 `False`，因此 10 秒後回 `TIMEOUT`，新 daemon 不會被啟動。
  - SC-12 只核准「最多等 10 s」，沒有核准「因此失敗」。
- **失敗情境**：共用實驗機上另一位使用者以 systemd-user 模式執行 serialwrap。本使用者在 on-demand、daemon 未執行時：
  - 執行 `serialwrap setup` 切換模式（`setup_cmd.py:735`）：0.3.2 會完成；0.4.0 回 `{"error_code":"TIMEOUT","phase":"reconcile_wait_old_exit"}`，exit 1。
  - 執行 `serialwrap daemon restart`（`cli.py:750`）：回 `restart_wait_old_exit`，exit 1。
- **重現**（假 procfs）：

  ```
  other user's daemon w/o --socket, my endpoint: None
  no daemon at all: False
  wait_old_daemon_gone (old daemon already stopped, pid unknown): False
  ```
- **確切修法**：
  - 掃描時略過 uid ≠ `os.getuid()` 的行程（以 `os.stat(f"{proc_root}/{pid}").st_uid` 判定）。
  - 同 uid 但不帶 `--socket` 的 daemon，以其預設 endpoint（依 `supervision_mode` 推得 canonical socket）比對，不要直接回 `None`。
  - 讀取失敗只在同 uid 行程上視為 incomplete。
  - 補兩案回歸。

### S1X-a-6 [Medium] `sw_core/serial_port.py:402-408`＋`service.py:699-705` — 一般使用者 daemon 的 `foreign_holders` 全面變形，repo 內兩個實機 case 因此崩潰或誤判

  - `realhw/acceptance/gate.py:_foreign_holder_violations` 已經正確處理新形狀，可作為參考。
- **重現**：


### S1X-a-7 [Medium] `sw_core/session_manager.py:2795-2860`（`_complete_drain`）— release／clear 後的 session 欄位與 0.3.2 不同

- **問題**：drain 化之後的收尾沒有沿用 0.3.2 的欄位更新。state 轉移相同，只有欄位不同（bind 完全相同）：
  - `session clear`（裝置在場）：0.3.2 為 `state:ATTACHING, last_error:null`；0.4.0 為 `last_error:"CLEARED"`，直到 attach 完成前 `session list` 都看得到。
  - `device release`：0.3.2 會更新 `detached_at` 並重置 `reprobe_attempts`／`reprobe_exhausted`；0.4.0 保留舊值。
- **重現**（同一初始狀態，base／fr 各跑 release／clear／bind，比較 `to_public_dict()`）：

  ```
  clear   base "last_error": null            fr "last_error": "CLEARED"
  release base "detached_at": "<now>", "reprobe_attempts": 0, "reprobe_exhausted": false
          fr   "detached_at": "OLD",   "reprobe_attempts": 2, "reprobe_exhausted": true
  ```

  `test_clear_and_bind_use_recovering_during_drain` 只驗 drain 期間的 RECOVERING，沒有驗收尾欄位。
- **確切修法**：
  - `_complete_drain` 的 clear 分支：裝置在場時設 `session.last_error = None`。
  - release 分支：設 `session.detached_at = now_iso()` 並呼叫 `self._reset_reprobe_progress_locked(session)`。
  - 補以 0.3.2 欄位為 oracle 的回歸測試。

### S1X-a-8 [Medium] `sw_core/session_manager.py:963-1003`＋`:1380` — template 已不存在的 RELEASED 紀錄永久阻擋裝置，CLI 無法解除
