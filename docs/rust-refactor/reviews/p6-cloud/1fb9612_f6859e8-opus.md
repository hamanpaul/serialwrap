### 03ba902 feat(rust-console): bridge 起來時建立 internal 哨兵 primary console（Task 9 步驟 5）
1. [Medium] `crates/sw-core/src/session_core.rs:2368-2377` 與 `crates/sw-core/src/session_core/console.rs:890` — 哨兵改成非同步建立。在哨兵登記前，session 就可能已經可以接受 attach。
   - Python 在 `start()` 的鎖內同步建立哨兵，任何 human console 都在它之後。
   - Rust 的流程：adopt 時只發出 `CreatePrimaryConsole`；passthrough 或非 command_capable 的 session 同一個 handler 內就進 `ATTACHED`；`PrimaryConsoleReady` 排在 control lane 後面。
   - 結果：已排在前面的 `ConsoleAttach` 會先成功，human 變成 primary、`vtty_cache` 指向 human，接著哨兵被 `ConsoleDiscard`。
   - 預期（Python）：`console_list` 含 `"primary"`、`vtty` 是哨兵路徑、`console_count` 為 2。
   - 實際（Rust）：沒有哨兵，`console_count` 為 1，human 死掉後 primary 變成 None。
   - 確切修法（二擇一）：
     - 在 executor 開 bridge 時同步建好哨兵 PTY，把 `PtyInfo` 放進 `BridgeOpened` 事件，core 在 adopt 的同一事件內登記；或
     - core 在 adopt 時先登記哨兵佔位，`PrimaryConsoleReady` 只回填 vtty 與 token；建立失敗時再移除佔位。
   - 並補一支在 passthrough 情境下「先排 attach 再處理 ready」的 core 測試。

### 7acf7f6 fix(rust-console): refresh 後重新評估 open、#56 interactive 命令拒絕與 hub 掃描 reap
1. [Medium] `crates/sw-core/src/session_core/lease_p6.rs:402-404` — ATTACHED 救援分支新增了回 `SESSION_BUSY` 的出口。
   - Python ATTACHED 分支（`session_manager.py:6936-6991`）不判斷前景、從不回 `SESSION_BUSY`。refresh 產生 `needs_resume` 時，它會同步執行 post 後 `retry`，結果是開出 recovery lease。
   - 07 D-22(4) 也明文要求 ATTACHED 分支「不判前景（Python parity）」。D-22(2) 的 SESSION_BUSY 只適用於 READY。
   - 具體情境：ATTACHED + bootloader prompt；c1 human lease 被 agent A 以 `timeout=1` soft preempt；c1 打 `Q`；時間推進 1.5 s；agent B `open(allow_attached=true)`。
   - 預期（Python）：`{"ok":true,"recovery_mode":true,…}`。
   - 實際（Rust）：`{"ok":false,"error_code":"SESSION_BUSY","selector":"COM0"}`。
   - 這條路徑也沒有任何回歸測試。
   - 確切修法：ATTACHED 分支不要回 busy；把 reply 暫存到 refresh 產生的 hold 結算後再重新評估（等價於 `retry_after_post`），或在 hold 仍在途時依 D-22(4) 撤銷後照常開 lease。補 `attached_refresh_created_replay_still_opens_recovery` 測試鎖定 Python 結果。
