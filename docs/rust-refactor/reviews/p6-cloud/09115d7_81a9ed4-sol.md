  - 機制：
    - 測試等待 probe 回覆的迴圈（`:1287-1295`）每輪無條件 `h.clock.advance(100 ms)`，再實睡 1 ms。
    - release 的 drain 逾時是假時鐘上的 `DRAIN_TIMEOUT_MS = 3000`（`crates/sw-core/src/resources.rs:38`、`session_core.rs:1238-1241`）。
    - drain 回條則由替身 executor 的 `worker.finish_async` 以實際時間完成（`tests/support/mod.rs:1034-1040`）。
    - 只要 probe 回覆或 drain 回條在實際時間上延遲約 30 ms 以上，假時鐘就會先超過 3000 ms。`DrainTimeout` 觸發後，`mark_drain_timeout`（`session_core.rs:3065-3080`）讓 release 回 `DRAIN_STALLED`／`ok=false`，與 gate 紀錄的「release 回 ok=false」一致。
  - 證據：在拋棄式副本（`git archive 81a9ed4`，只在斷言訊息加印 release 回覆與本輪假時鐘推進量，產品碼未動）實跑。
    - 一般負載單跑 1000 輪通過。其中 TARGET_UNRESPONSIVE 輪的假時鐘推進量為 4600～4700 ms，已經超過 3000 ms；這些輪能通過，只是因為 drain 回條在實際時間上先到。
    - 加 6 個 `yes` CPU 佔用、4 路並行，共跑 12 次，其中 1 次失敗。失敗在第 379 輪：probe 回 `OK`，但本輪假時鐘已推進 4500 ms；release 回 `{"ok": false, "error_code": "DRAIN_STALLED", "drain_stalled": true, "drain_timeout_epoch": 380, ...}`。
    - 實作者記錄的同範圍重跑與 200 次壓測都在低負載下進行，皆 0 敗。原因在此：這個失敗需要排程延遲才會出現。
  - 性質：測試替身的時鐘推進與實際時間的回條競態，不是產品行為或 Python 1:1 缺陷。drain 超過 3 s 回 `DRAIN_STALLED` 本身是正確行為。
