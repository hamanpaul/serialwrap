### 6eafa6a feat(rust-console): interactive lease 承接 human lease、stash 與可重複讀 tombstone

1. [Medium] `crates/sw-core/src/session_core/lease_p6.rs:328-341` — READY 分支先檢查 `foreground_busy()`，然後才 `refresh_lease_p6()`。refresh 可能惰性結束一個已過期、帶 stash 的 agent lease，並在這時建立新的回放 hold。程式之後沒有重新評估，直接走 soft preempt，`revoke_replay()` 會把剛建立的回放撤銷。
   - 輸入：READY，c1 human lease；agent A `open(timeout=1.0)` 觸發 soft preempt；c1 打 `Q`（進 deferred）；`clock.advance(1.5s)`，Tick 還沒投遞；agent B `interactive_open(owner="agent")`。
   - Python（`session_manager.py:6849-6851` 的 retry 迴圈）：`post.execute()` 先同步把 `Q` 寫上 UART，重新評估後 B 才 soft preempt 成功。
   - Rust：B 回 `ok:true, soft_preempted:true`，`Q` 被 `ReplayRevoked` 重新 defer，要等 B close 之後才寫出。結果是 UART 位元組順序與 Python 相反，也違反計畫 Step 3.1「先在 core 內執行 resume 效果，再重新評估一次」和 D-22(2)（hold 期間 READY open 應回 `SESSION_BUSY`）。
   — 修法：refresh 之後若 `foreground_busy()` 從 false 變成 true（新的未撤銷 hold），回 `selector_error("SESSION_BUSY")`；或照計畫用最多兩輪的 retry 重新評估。並補一個回歸測試涵蓋上面的輸入。

2. [Medium] `crates/sw-core/src/session_core/lease_p6.rs:141-145`，另見 `session_core.rs` 的出列與 `execute_time_reject` — parity #56 和 D-22(2) 例外規定：tick 到期還原結算前，「interactive 模式 `command.submit`、human 救援」也要回 `SESSION_INTERACTIVE_BUSY`（`session_manager.py:6407`、`:6585`）。目前 `tick_close_hold` 只在 `interactive_open`、`console_attach`、human reboot 三處檢查。interactive 模式命令在 hold 期間只是排隊，結算後照常開 lease。
   - 輸入：同 `tick_close_restore_returns_session_interactive_busy` 的前置，在回放 `T` 還沒結算時提交 `mode="interactive"` 的 `vim`。
   - Python：`{"ok":false,"error_code":"SESSION_INTERACTIVE_BUSY"}`。
   - Rust：結算後開 lease，回 `ok:true`。

   — 修法：在 interactive 模式命令的 execute-time 路徑（還有之後的 human 逾時升格路徑）加上 `tick_close_hold.is_some()` 的拒絕判斷，回應不帶 selector；並在 `tick_close_restore_returns_session_interactive_busy` 補上這一案。

3. [Low] `crates/sw-core/src/session_core/lease_p6.rs:389-398` — ATTACHED 分支在確定能開 lease 之前，就無條件 `revoke_replay()`。若接著命中 `Some(_) => busy_reply()`（既有 agent lease），open 被拒絕，回放授權卻已撤銷，被撤銷的 bytes 會留在 deferred，直到下一個回放點才送出。
