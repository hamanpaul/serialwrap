## B 新發現

1. **V051-95ad179-1 [High]** [runtime_paths.rs:198](crates/sw-proto/src/runtime_paths.rs:198) — 舊來源基準會在設定值改回原字串時復活，WAL 寫到錯誤目錄。

   例如 system config 的 `wal_dir: archive/wal` 被複製到 `/user/config.yaml`，中繼資料記錄來源 `/system/config.yaml`。使用者把值改為 `other/wal` 並啟動後，解析為 `/user/other/wal`；之後再改回 `archive/wal`，預期應以目前設定檔解析成 `/user/archive/wal`，實際卻因字串重新相等而回到 `/system/archive/wal`。doctor 使用同一解析器，也可能將錯誤路徑判為一致。直接呼叫目前解析器已重現此結果。

   **修法：**在設定值與來源紀錄不符時永久失效或清除舊來源紀錄，且不能只靠字串相等判定其仍有效；補上「原值 → 新值 → 原值」跨啟動及 doctor 比對的回歸測試，同時保留未編輯複本的原基準。

2. **V051-95ad179-2 [Medium]** [config_types.rs:968](crates/sw-proto/src/config_types.rs:968) — 複製設定時會覆寫既有的同名非 mapping 設定值。

   例如 system config 含 `wal_dir: archive/wal` 與 `__serialwrap_internal: keep-this`，呼叫新增的來源記錄邏輯後，後者被整個換成 mapping，原值消失；直接執行設定物件的序列化已確認。這違反 BC-17 不改其他設定鍵的條件。

   **修法：**讓來源紀錄避免佔用或覆寫既有使用者資料；遇到名稱或型別衝突時保留原值，並補上衝突設定的複製與重啟測試。

3. **V051-95ad179-3 [Medium]** [daemon_process.rs:263](crates/sw-daemon/tests/daemon_process.rs:263) — 兩份 daemon 修前紅燈的測試檔內容無法追溯到所交付的測試 commit。

   兩份 log 記錄測試檔 SHA-256 為 `24b96924…`，但 `bd9409e3` 與目前 `95ad1798` 的該檔均為 `5d945238…`；log 所記起點 `413e02f3` 為 `da18687d…`。因此可確認當時有紅燈，但無法僅憑現有 commit 還原實際執行的測試檔。doctor 紅燈的測試檔雜湊則與提交版本一致。

   **修法：**使用可由 commit 還原的測試版本，在 `413e02f3` 產品碼上重跑這兩項紅燈，保存命令、產品碼 commit、測試檔雜湊與結果，再核對修後綠燈。
