## B 新發現

**V051-a0b00f2-1 [High]** — [rollback.rs](crates/sw-cli/src/rollback.rs:3669) — 中斷復原重新從當次環境解析 config 路徑，但 journal 的 `config_sha256: None` 只代表**原交易路徑**不存在。具體情境：首次安裝使用 `SERIALWRAP_CONFIG=A`，A 原本不存在，交易寫入 A 後中斷；下次以同一安裝根、`SERIALWRAP_CONFIG=B` 執行 setup，而 B 是使用者既有的合法設定。復原會在 [setup_cmd.rs](crates/sw-cli/src/setup_cmd.rs:1914) 執行，隨後依 `None` 分支刪除 B；A 則仍存在。這會造成無關設定資料遺失。

確切修法：在 journal 綁定原交易實際使用的 config 路徑及必要的建立狀態；復原只操作該路徑，對路徑不一致或無法確認檔案屬於交易的情況保留 journal 並 fail closed。補中斷後切換 `SERIALWRAP_CONFIG` 的測試，確認 B 不變、A 被正確處理或交易安全停止。

**V051-a0b00f2-2 [High]** — [rollback.rs](crates/sw-cli/src/rollback.rs:3672) — 本輪將既有 config 的回復來源由保留 metadata 的 backup 改成 snapshot，但 [snapshot 建立](crates/sw-cli/src/rollback.rs:828)使用 `atomic_write(..., None)`；POSIX 實作將其設為 [`0600`](crates/sw-pal/src/fs_ops/posix.rs:43)。例如原 config 為 `0640`、由其他帳號透過群組讀取，升級切換失敗後，回復檔變成 `0600`，讀取者失去存取權；SHA 驗證仍通過。修正前完整 backup 路徑使用 `copy_preserving`，會保留原模式。

確切修法：保存並還原原始權限等必要 metadata；完整且驗證過的 backup 可作為來源，或讓 snapshot 本身保留原始 metadata 並驗證。補 POSIX 測試，對既有 `0640` config 注入切換失敗與中斷復原，分別核對內容與模式。
