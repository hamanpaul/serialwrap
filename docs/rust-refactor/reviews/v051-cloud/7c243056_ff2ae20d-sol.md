## B 新發現

1. **V051-ff2ae20-1 [High]** [uart_bridge.rs:488](crates/sw-core/src/uart_bridge.rs:488) — **多行 secret 合計超過上限時，第一個 RX 行尾會解除後續行的遮罩。**例如同一 active snapshot 下，deferred 依序收到 600 bytes secret、`\r`、另一筆 600 bytes secret；兩筆都在收到回顯前完成回放。第二筆登記使總量超過 1024，進入 `overflow_mask_line`。DUT 之後回顯第一筆及 `\r\n`：第一個 `\r` 在沒有在途寫入時清除 overflow 狀態與排隊 matcher；接著第二筆回顯經 [uart_bridge.rs:605](crates/sw-core/src/uart_bridge.rs:605) 明文發布至 RX 出口。預期兩筆均不得洩漏；現有上限測試只驗證單一 RX 行。

   **修法：**保留有界的待處理 secret 行數或等效狀態；超限後，在所有已登記且尚未安全結束的行完成前持續 fail-safe 遮罩，不能由第一個行尾清除後續行的保護。補受控 deferred 多行超限測試，驗證 RX WAL、event、console、agent log 及 TX META。

2. **V051-ff2ae20-2 [High]** [uart_bridge.rs:634](crates/sw-core/src/uart_bridge.rs:634) — **未完整回顯的前一筆 secret 遇到行尾時，會無條件被下一筆 matcher 取代。**例如兩筆已分類 secret 為 `alpha\r` 與 `bravo`，兩筆均已登記後，DUT 因終端重繪依序輸出 `al\r\nalpha\r\nbravo`。`al` 會被遮罩，但第一個行尾立即丟棄 `alpha` matcher、切換到 `bravo`；後續完整的 `alpha` 因不符合 `bravo` 而明文進入 RX 出口。預期已登記的第一筆 secret 後續完整回顯仍應遮罩。現有新測試在第二筆登記前就先注入第一段前綴與行尾，沒有覆蓋兩個 matcher 已同時排隊的交錯。

   **修法：**行尾結算已匹配前綴時，保留仍可能延後回顯的前一筆 matcher，並以有界、fail-safe 的方式同時辨識後續已登記 secret；不得僅因遇到行尾就丟棄尚未完成的保護。補上述受控重繪案例，逐一檢查四個 RX 出口與輸出順序。
