### fa7e409 feat(rust-pal): 新增跨平台事件 handler 子程序執行器

1. **[Medium] `crates/sw-pal/src/process/handler_posix.rs:62` — POSIX 上 ENOEXEC 的處理和 Python 不同**
   - 問題：
     - `std::process::Command` 設了 `pre_exec`，就會走 fork 後 `libc::execvp` 的路徑。
     - glibc 的 `execvp` 遇到 `ENOEXEC`（可執行但沒有 shebang、也不是 ELF）時，會改用 `/bin/sh <file>` 再執行一次。
     - Python 的 `_posixsubprocess` 自己走 PATH、直接呼叫 `execve`，不做這個後備，會丟出 `OSError(8)`。
   - 具體輸入：`handler.exec: ["/path/noshebang"]`，檔案內容為 `echo RAN-AS-SH\nexit 4`，權限 0755。

     | | Python | Rust |
     |---|---|---|
     | 事件 | `{"type": "fire_failed", …, "reason": "[Errno 8] Exec format error: '/path/noshebang'"}` | `fire_completed`，`exit_code: 4`，`stdout_tail: "RAN-AS-SH\n"` |
     | counter | `fires+1` | `fires+1` |

     上表已實測重現。對 handler 作者來說可觀察的差異是：Python 上會失敗的規則，在 Rust 上卻「成功」執行了。
   - 確切修法：
     1. 在 fork 前，依 spec.env 的 `PATH` 預先組好候選路徑的 `CString` 陣列，以及 argv／envp 的指標陣列。spec.env 沒有 `PATH` 時，用 `os.defpath` 的 `/bin:/usr/bin`；argv0 含 `/` 時只取它本身。
     2. 在 `pre_exec` closure 做完 setsid 與 CLOEXEC 之後，逐一呼叫 `libc::execve`。只記錄第一個不是 ENOENT／ENOTDIR 的 errno，全部失敗就回傳 `Err(io::Error::from_raw_os_error(saved_or_last))`，交給 std 的 CLOEXEC 錯誤 pipe 回報。這個路徑不得配置記憶體。
     3. `spawn_error` 維持 `with_filename(argv0)`，對應 Python 的 `err_filename = orig_executable`。
     4. 在 conformance 新增 POSIX 限定的 `spawn_enoexec_is_python_like`：建立沒有 shebang 的 0755 檔案，斷言 `SpawnFailed.py_message == "[Errno 8] Exec format error: '<path>'"`。用 add-only 方式登記到 L1 鎖，並且先證明修正前這項測試是紅的。

2. **[Low] `crates/sw-pal/src/process/handler_posix.rs:65` — 子程序 environ 的順序被排序**
   - 問題：std 的 `CommandEnv` 以 BTreeMap 存放 env，`execve` 收到的 envp 是依鍵排序的。Python 依 dict 插入順序傳入：先放白名單鍵，再放 `SERIALWRAP_EVENT_SCHEMA_VERSION…SCOPE` 的固定順序。
   - 影響：handler 跑 `env`，或讀 `/proc/self/environ`，看到的順序和 Python 不同（探針已實測）。功能值相同，只有呈現順序不同。
   - 確切修法：
     - 方案一：併入 M1 的 `pre_exec`＋`execve` 改寫，envp 直接依 spec.env 的 Vec 順序組成。
     - 方案二：在 `contracts/behavior_changes.yaml` 登記成 Rust-only 呈現差異。

3. **[Low] `crates/sw-pal/src/process/handler_windows.rs:107` — 子端 pipe handle 在 CreateProcessW 前已設成可繼承，會洩漏給其他同時 spawn 的子程序**
   - 問題：
     - HANDLE_LIST 只限制「本次」CreateProcessW 繼承哪些 handle。
     - 同一個 daemon 裡還有其他不帶 HANDLE_LIST、`bInheritHandles=1` 的 spawn，例如 `process/windows.rs:198` 的 ProcessCtl，以及 `sysenv/windows.rs` 與 `com0com.rs` 的 `std::process::Command`。
     - 如果這些 spawn 剛好落在這個時間窗內，就會一起繼承 handler 的 stdout／stderr 寫端。結果是 reader 等不到 EOF，handler 本身早已結束，事件卻被誤報成 `fire_timeout`。
   - 確切修法：
     - 在 sw-pal 內設一把 Windows 共用 spawn mutex，`handler_windows::spawn`（從 CreatePipe 到 CreateProcessW 後關閉子端）與 `process/windows.rs` 的 CreateProcessW 都要持有。
     - 其餘 std `Command` 的呼叫點改走同一把鎖；或至少把這項登記到 P7-LW-6 的觀察項。

4. **[Low] `crates/sw-pal/src/process/handler_windows.rs:325` — Windows exit code 被轉成 i32**
   - 問題：`code as i32` 讓 NTSTATUS 類的 exit code 變成負數，例如 0xC0000005 會成為 `-1073741819`。Windows 上的 Python `returncode` 是不帶號的 DWORD（`3221225477`）。
   - 背景：這是 Rust-only 路徑，`HandlerOutcome.exit_code: i32` 也已凍結。
   - 確切修法：在 design-event-trigger 的「Windows handler 語意」段註明 `fire_completed.exit_code` 以有號 32 位元呈現；或由 dispatcher 在 Windows 上以 `u32` 還原後再 emit。兩者擇一並登記。

5. **[Low] `crates/sw-pal/src/process/handler_windows.rs:66` — 用 argv 內容推斷 shell 形式**
   - 問題：`handler.exec: ["cmd.exe","/d","/s","/c","…"]` 也會被當成 shell 規則，不套 MSVC 跳脫，和文件寫的「exec 依 MSVC 規則」不一致。
   - 確切修法：在 design-event-trigger 註明這個等價規則。凍結的 `HandlerSpec` 不另加旗標。

### 91109e7 feat(rust-event): 承接事件 dispatcher 子程序池

1. **[Low] `crates/sw-core/src/event_engine/dispatcher.rs:225`／`:411` — `stop` 在 worker 註冊 `running` 之前的時間窗裡 abort，會漏掉這個 handler**
   - 問題：
     - worker 從 `recv` 開始，經過 `counters.load`、組 payload，到 `running.insert` 為止，這段期間 inflight 已經算進去，但 `running` 還沒有它。
     - `stop` 在這段期間逾時的話：
       - `aborted` 會把它算進去，但它其實沒有被 trigger；
       - 之後它照樣 spawn 新的 handler，而且不受 abort 控制；
       - 結果是被列為 unreaped，並在 daemon 結束後繼續存活。
     - 這違反 SC-11 細化「逾時終止仍在跑者」的契約。
   - 確切修法：
     - `State` 加 `aborting: bool`。`stop` 在 trigger 迴圈前，於同一把鎖內設成 true。
     - `run_inner` 在 `running.insert` 的同一把鎖內檢查它，為 true 就先 `abort.trigger()`。之後的 `run` 會立即回 `TimedOut`，和其他被 abort 的 handler 同樣路徑。
     - 補測試：用 `set_hook` 在 `counters.load` 前阻塞的變體不可行，所以改在 `CounterStore` 注入慢 fs。

2. **[Low] `crates/sw-core/src/event_engine/dispatcher.rs:204` — 非 UTF-8 的環境值被以 lossy 方式替換**
   - 問題：`SysEnv::var` 用 `to_string_lossy`，所以 `PATH`／`HOME` 裡的非 UTF-8 位元組會被換成 U+FFFD 再傳給 handler。Python 的 `os.environ` 以 surrogateescape 原樣傳遞位元組。
   - 背景：凍結介面是 `(String, String)`，實際上很少遇到。
   - 確切修法：在 `behavior_changes.yaml` 登記成已知差異；或日後在 `HandlerSpec` 以 add-only 方式新增 OsString env。

3. **[Low] `crates/sw-core/tests/event_dispatcher.rs:507` — 斷言上限比計畫寬鬆**
   - 問題：計畫表格要求 `stop(now+200ms)` 在 ≤ 300 ms 內返回，測試放寬到 400 ms，也沒有寫理由。
   - 背景：blocking 模式 abort 後約 5 ms 就返回，300 ms 可以做到。`:571` 的 ignore_abort 本身就需要 200＋100 ms，放寬到 400 ms 合理，但應該註明。
   - 確切修法：`:507` 改回 `<= Duration::from_millis(300)`；`:571` 加註解說明寬限 100 ms 的排程餘裕。
