### bc82b94 feat(rust-reprobe): 承接 readiness reprobe 與 bootloader 卡死判定

逐步對照 `_prepare_reprobe_locked` 的 13 步後，`prepare`、`record_attempt`、`reset`、`target_still_valid`、`bootloader_evidence` 的決策都與 Python 一致。golden 包含 43 列 decisions（prepare 27、record 10、finish 6）與 18 列 valid，逐列比對。`auto_reprobe_converge` 對 `Raised`、`TxIncomplete`（→ `REPROBE_FAILED:<型別>`，記一次 attempt，不經 finish）、`Aborted(Refused|Cancelled)`（對應 `probe_refused`：READY 保留，其餘 ATTACHED＋PROMPT_UNAVAILABLE）的映射，與 `_spawn_reprobe_probe`／`_probe_existing_bridge` 一致。`login_quiet::login_failure_code_table` 的三列只是把一次性回應改成持續性比對，斷言值沒有改變，不算削弱。

發現：

1. [High] `crates/sw-core/src/session_core.rs:2697-2716`（`apply_quiet_armed`）與 `:2987`（`auto_reprobe_finished` 開頭的世代檢查）— **自動重探進行中遇到 quiet arm，session 會永久卡住。** 情境是 ATTACHED 的板子重開機，這正是本功能要處理的 boot 情境：probe 期間 banner 到達，quiet arm。
   - `apply_quiet_armed` 只在 `run.kind == Attach` 時累加 `quiet_bumps`，AutoReprobe run 的 `quiet_bumps` 與 `exempt_bumps` 都維持 0，但 `generations.fsm_gen` 已經 +1。
   - FSM 之後以原世代回報 `LoginFinished` 時，`login_gen_current` 回 false，`auto_reprobe_finished` 直接 `return Vec::new()`。結果是 `login_run` 沒被 take、`reprobe.inflight` 維持 true、attempt 沒有記錄。
   - 後續 `reprobe_tick` 在 `login_run.is_some()` 時一律早退，所以永遠不再重探。
   - 在這段期間到達的手動 `session attach`／`recover` 會依本 commit 的新邏輯掛到這個 AutoReprobe run 的 waiters 上，**RPC 永遠不回覆**，直到 bridge 關閉或 drain。
   - 反證 H-1 已實測重現。

   Python 的對應行為：`_login_tx_refused` → `probe_refused` → ATTACHED＋`PROMPT_UNAVAILABLE`（READY 則保留），接著 `_finish_probe_reprobe` 記 attempt＝1，`finally` 清除 `_reprobe_inflight`。quiet 到期後重探恢復，手動 attach 取得 probe 鎖後照常回覆。

   預期輸出（同一輸入）：`reprobe_attempts=1`、`next_reprobe_at` 非 null；quiet 到期且 RX 安靜 ≥3 s 後再發出 StartLogin；`SessionAttach` 在 auto run 收斂後以新世代 probe 並回覆。

   修法：比照既有 `LoginRunKind::Reprobe` 的「結果一律回填」。
   - `auto_reprobe_finished` 改為只要求 `conn_epoch == Some(epoch)` 且 `login_run` 的 `epoch`／`fsm_gen` 等於回報值，不再呼叫 `login_gen_current`。
   - 世代已被 quiet 推進時，把結果當成 `LoginOutcome::Aborted(LoginAbort::Refused(..))` 交給 `auto_reprobe_converge`。這樣 READY 會保留，ATTACHED 則落 `PROMPT_UNAVAILABLE` 並經 `finish_auto_reprobe` 記 attempt、清 inflight。之後照原樣重派 deferred waiters。
   - 另補回歸測試 `quiet_arm_during_auto_reprobe_settles_and_resumes`：斷言上述三個預期輸出，並斷言手動 SessionAttach 有回覆。

發現：

1. [Low] `crates/sw-core/src/transport_stall.rs:96`（`after.saturating_sub(before)`）— Python 是 `rx_after - rx_before`，計數倒退時結果為負，`!= 0` → 不翻轉。Rust 以 saturating 截為 0，反而可能翻成 TRANSPORT_STALL。正常情況下 bridge 計數單調，所以只是理論差異。修法：`let delta = after.checked_sub(before).map_or(1, |d| d);`，或直接以 `after != before` 判定零 RX，避免負值被當成零 RX。

2. [Low] `crates/sw-pal/src/device_source/usb_posix.rs:46-48` — 註解宣稱「`os.path.realpath` 不存在時回原路徑；原路徑段不會命中 busid」，這在一般情況下不成立。Python `realpath` 仍會解析存在的前綴 symlink：Linux 的 `/sys/class/tty/<name>` 本身就是指向 `/sys/devices/.../1-1/1-1:1.0/ttyUSB0/tty/<name>` 的 symlink，即使 `device` 不存在，Python 仍可能找到 `1-1`。Rust 的 `canonicalize` 整條失敗後退回未解析的路徑，所以回 None。真實 USB tty 都有 `device` 連結，實務上影響很低。修法：失敗時改為 canonicalize 最長存在的祖先再接回剩餘段（等價於 `os.path.realpath(strict=False)`），並修正註解；另加一個 tempdir 測試：`class/tty/ttyX` 是 symlink 且沒有 `device` 時預期 `"1-1"`。

3. [Low] `crates/sw-pal/src/fs_ops.rs:90-121`（`with_filename` 的 repr）— 只跳脫 `<0x20` 與 `0x7f`。Python `repr(str)` 還會跳脫非 printable 的 Unicode 字元（例如 `\x80`-`\x9f`、` `），所以檔名含這類字元時訊息會不同。這只是邊角情況。修法：加上 `c.is_control()` 或依 `unicodedata` 非 printable 類別輸出 `\xNN`／`\uNNNN`／`\UNNNNNNNN`，或直接重用 `sw_proto::pyfmt` 既有的 `py_repr_str`（如果有）。

4. [Low] `crates/sw-pal/tests/usb_topology.rs:35`（`usb_windows_is_always_none`）— 這是 Windows 測試，沒有登記在 `l1_required.lock.json` 的 Windows gate，lock 只新增了 POSIX 的 `busid_from_sysfs_tempdir`。Task 19 收斂 Windows 證據時容易漏掉。修法：在 Windows 原生證據到位的同一個 PR，把 `cargo:sw-pal::usb_topology::usb_windows_is_always_none`、`fs_ops_p7::*` 以 add-only 方式登記到 Windows gate 段。
