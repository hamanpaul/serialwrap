## B 新發現

**P7-62e430d-1 [Medium]** [scripts/rust/p7_case_coverage.py:242](scripts/rust/p7_case_coverage.py:242)（另見 `:222-230`、[scripts/rust/p7_gate.sh:98](scripts/rust/p7_gate.sh:98)、[scripts/rust/slice21_gate.sh:59](scripts/rust/slice21_gate.sh:59)、[tests/test_p7_ab_report.py:260](tests/test_p7_ab_report.py:260)）

**問題**：新的來源綁定要求 slice21 `report.json` 的 `identity.daemon_sha256` 必須等於 P7 快照的 serialwrapd sha256。但兩個 gate 測的是不同的建置產物：

- slice21 gate（`slice21_gate.sh:59`、`:279`、`:467`）建置並測試 `target/x86_64-unknown-linux-gnu/release/serialwrapd`，`assemble --daemon-path` 也是把這個 release 檔的 sha256 寫進 identity。
- P7 gate（`p7_gate.sh:95-98`）用 `cargo build --workspace --bins` 建置，再把 `target/debug/serialwrapd` 快照到 `artifacts/serialwrapd`。
- 兩個腳本都沒有提供覆寫 daemon 路徑的參數。

同一個 commit 的 debug 與 release 建置不可能有相同的 sha256，所以在正式流程中，2.1 先前切片案例的匯入一律不採用，這些案例永遠記缺漏，coverage 列永遠 FAIL。也就是說，rulings/p7.md SPEC-GAP #4 (ii) 裁定的承擔機制（匯入 slice21 gate 的逐案證據）實際上無法使用，P7 gate 永遠到不了 PASS。

這個問題沒有被測出來，原因有二：

- 新回歸讓兩邊共用同一個常數 `DAEMON_SHA`，假設了實際上不存在的情形。
- 實作者以 r13b 重算 coverage 時沒有提供 slice21 run，所以結果看起來「不變」。

**具體失敗情境**（實測，HEAD `62e430d`，`CARGO_TARGET_DIR=/tmp/solrev-p7-target`）：

1. 依兩支腳本各自的建置命令建置：
   - `cargo build --workspace --bins` 得到 debug `serialwrapd`，sha256 `6eb9b818…`。
   - `cargo build --release -p sw-daemon -p sw-cli --target x86_64-unknown-linux-gnu` 得到 release `serialwrapd`，sha256 `2c41993a…`。
2. 建立兩邊的證據：
   - P7 端：debug 檔快照到 `p7run/artifacts/serialwrapd` 後，以 `p7_gate_report.init_results` 產生 `results.json`（`git_head` 為 `62e430d4…`）。
   - slice21 端：以 `slice21_gate_judge.build_identity(daemon_path=<release>)` 組 identity，`report.json` 的 `git_revision` 為 `62e430d4…`，`case_verdicts.json` 中 13 個 2.1 案例全為 PASS。
3. 執行 `p7_case_coverage.build(..., slice21_run=..., p7_results=...)`。
   - 預期：同一 commit 的 slice21 gate 逐案 PASS 被採用，13 案記 PASS。
   - 實際：`prior_sources["2.1"].accepted == false`，原因為「slice21 gate report.json daemon sha256 2c41993ad244 與本 gate 快照 6eb9b8185881 不符」，13 案全為 GAP。

**修法**（擇一）：

- (a) 讓 P7 gate 綁定與 slice21 相同類型的產物，並保留 sha 綁定：
  1. `p7_gate.sh` 第 0 步另外以 slice21 相同的命令建置 release daemon，快照到 run 目錄。
  2. 在 `results.json` 以獨立鍵記錄它的 sha256，例如 `prior_slice_artifacts.serialwrapd_release`。不要放進 `artifacts`，否則 `_p7_identity` 的 `len(daemon) == 1` 會失效。
  3. `_bind` 改為比對這個 release sha256。
- (b) 改為只綁定原始碼：
  1. 要求 `git_revision == git_head`。
  2. 要求 slice21 報告自身的身分檢查通過：`identity_problems` 為空、`identity.build.daemon_sha256_at_build == identity.daemon_sha256`、`dry_run` 為 false。
  3. 在文件中寫明「slice21 測的是同一 commit 的 release 建置」。

兩案都要把回歸 fixture 改成兩邊 sha 不同的真實情形：P7 端是 debug 快照，slice21 端是 release。(a) 斷言 release sha 相符時採用；(b) 斷言同 commit 即採用。另外，P6 日後為 s22 輸出補 `identity` 時，要比照同一規則，避免 2.2 重演此問題。

**P7-62e430d-2 [Low]** [scripts/rust/p7_case_coverage.py:256](scripts/rust/p7_case_coverage.py:256)（另見 `:264`）

**問題**：匯入時只核對 `report.json` 的身分欄位，不核對 `case_verdicts.json` 是否與該份 `report.json` 一致。`report.json` 自帶 `case_uptake.pass_case_ids`（`slice21_gate_judge.py:342-357`，依同一份 verdicts 算出），但沒有被拿來比對。

**情境**：

- 在 P7-62e430d-1 修正後，把同一 run 目錄中的 `case_verdicts.json` 改寫或重新產生，而不重新 `assemble`。例如事後補匯入證據時只重跑 `slice21_gate_judge.py case-verdicts`。此時報告中判為非 PASS 的案例會被 coverage 記為 PASS。
- 新回歸的 docstring 宣稱「手寫 verdicts 一律不採用」，但實際只測了「缺 `report.json`」這一種情形。

**修法**：

- 對 `report.json` 的 `freeze` 案例集合，要求 `case_verdicts.json` 中判為 PASS 的案例與 `case_uptake.pass_case_ids` 相等，不一致就不採用。
- 或改為直接以 `report.json` 的判定為準。
