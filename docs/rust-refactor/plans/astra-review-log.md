### 整合時處理的交叉一致性

- `spec-reconciliation.md` UIO-12.2-c 原寫 Python「`_state_lock` 內 `os.write`」，與 02 T20 的 `_tx_fence_lock` 設計矛盾，已改為 `_tx_fence_lock` 臨界區、`_state_lock` 只做 pre-check。
- R0-F2 × R0-F3 交互：06 `cap_posix_pty__holder_exit_releases_flock_excl_persists_while_master_open` 由父程序預持保活 fd，鎖後重掃會把它識別為外部 holder 使子程序 `Held`；改為子程序以 test-fakes 專用 `PosixSerialBackend::with_uart_exclusive(NoHolders)` 開啟，並寫入 Task 2 實作說明。
- 06 Task 2 鎖後重掃說明的拒絕路徑由「`guard` drop（close fd）」改為「`ExclGuard` drop（`TIOCNXCL` → close fd）」，與 R0-F3 關閉序一致。
- 03 P2 gate `resources` 列「`status: frozen`（該平台）」改為 key 層級凍結、讀 `per_platform[platform]`，與 R0-F5 的「不支援單一平台先凍結」一致。

### 已知未處理（範圍外，留待後續輪次或擁有者）

- 05 `supervision-mode set --force`（SC-22）仍可覆寫 FLASHING 後由 reconcile 停 daemon，風險與 R0-F4 同類。
- P4（05 Task 12）busy 錯誤碼為 `SESSION_BUSY`，P8（09 Task 14）為 `UPDATE_BUSY`；後者未見於規格 §9.2，需統一。
- R0-F3 `TIOCNXCL` 非 hangup 類 errno 的處理（照常關 fd、回報 `excl_cleared:false`）為實作者取捨，待擁有者確認；「SIGKILL 後 PTY master 仍開時 TIOCEXCL 殘留」的 kernel 行為尚未實跑驗證。
- 外部 flasher 自設 TIOCEXCL 後未清除即離開，下一次 flasher open 得 EBUSY（`endpoint_reopen_after_flasher_set_excl_recorded` 只記錄，DF 候選）。
